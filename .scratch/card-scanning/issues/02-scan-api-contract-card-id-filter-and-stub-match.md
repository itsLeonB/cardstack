# 02: Scan API contract: card id filter and live stub match endpoint

**Category:** enhancement
**Status:** ready-for-agent

**Blocked by:** None (can start immediately)

Spec: `.scratch/card-scanning/spec.md`.

## Agent Brief

**Category:** enhancement
**Summary:** Add the two backend pieces the scan screen needs: a way to fetch Cards by id from the catalog, and a live match endpoint with its final response shape that returns random Cards until the real matcher exists. Backend only.

**Current behavior:**
`GET /catalog/cards` filters by name, Expansion Set, card number, rarity, category and tag, but has no way to ask for specific Cards by id. The Collection entries search has a repeatable card id filter, but it only returns Cards already in that Collection. There is no match endpoint.

**Desired behavior:**
1. The catalog card search accepts a repeatable `cardId` filter (at most 100), combined with the other filters, mirroring the same filter on the Collection entries search. A Guest keeps their existing limits.
2. A new authenticated `POST` route takes one uploaded image and returns ranked candidates plus a `confident` flag. Each candidate carries a score and a card summary: id, name, Expansion Set, card number and hosted image address. The response schema is final: replacing the stub with the real matcher (ticket 06) must change no frontend code.
3. The stub returns random Cards from the catalog and writes nothing. About half of calls return `confident: true` with the first candidate as the match; the rest return `confident: false` with three to five candidates and plausible, descending scores.
4. The route validates the upload: a body size cap, an accepted image type, and an empty or non-image body is a 400 with the existing error classification. Authentication and the global CSRF guard apply as for other mutating routes; a Guest or an invalid token is rejected as on other authenticated routes. The existing rate limiting applies.
5. There is no backend switch for the stub; it is simply replaced later. The uploaded image is processed in memory and never stored.

**Key interfaces:**
- The catalog search spec and DTO gain the `cardId` filter, reusing the validation limits of the equivalent filter on the Collection entries search.
- A new match service, with request and response DTOs and its own repository call for picking random Cards. Follow the backend conventions for the domain, DTO and mapper packages, mocks and the `(ctx, dto)` service signature.
- Regenerate `openapi.json`, so the frontend client can be generated from the final schema.

**Acceptance criteria:**
- [ ] `GET /catalog/cards` with one or more `cardId` values returns exactly those Cards, combined with other filters, and rejects more than 100 ids
- [ ] The match route requires authentication and the CSRF header: no token is 401, a bad token is 401, a missing CSRF header is 403
- [ ] A valid image returns the documented schema, with both the confident shape and the candidate-list shape observed over repeated calls
- [ ] An empty body, a non-image body and an oversized body are rejected with the documented client errors
- [ ] Unit tests with mocked repositories cover the service; a real-Postgres route test covers the flow end to end
- [ ] `go build ./...`, `go vet ./...`, `gofmt -l .` and `go test ./...` pass and `openapi.json` is regenerated

**Out of scope:**
- Any frontend change (tickets 03 and 04 consume this)
- Embeddings, pgvector, a provider client, or any real matching (tickets 05 and 06)
- Rate-limit tuning beyond the existing mechanism
