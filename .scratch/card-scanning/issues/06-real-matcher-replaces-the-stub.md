# 06: Real matcher replaces the stub

## Agent Brief

**Category:** enhancement
**Summary:** The match endpoint stops returning random Cards and returns real matches: it embeds the uploaded photo, finds the nearest catalog Cards, and sets `confident` from the server-owned rule. The response contract does not change, so the frontend needs no change. Backend only.

**Current behavior:**
After ticket 02 the match endpoint returns random Cards with random confidence. After ticket 05 the catalog has embeddings but nothing searches them.

**Desired behavior:**
1. The match service embeds the uploaded image through the provider boundary from ticket 05, then runs a nearest-neighbour search over the stored embeddings of the current model only, and returns the top candidates ranked by score with their card summaries, in the same response shape as the stub.
2. `confident` is true only when the top score clears the configured threshold and the runner-up is clearly behind it by the configured margin. A near-tie, such as the same artwork reprinted across Expansion Sets, is non-confident and is never auto-picked. The threshold and margin are configuration values, initially set from ticket 07's recommended rule, so they can be tuned without a frontend release.
3. Cards with no embedding are simply not matchable. Only Indonesian Cards exist in the catalog, so no foreign-edition handling is built or tested.
4. The uploaded image is processed in memory and never stored. A provider failure or timeout returns a clear, classified error without leaking provider details, and the frontend's existing "match service unavailable" message covers it.
5. The stub's random-selection code is removed in the same change.
6. The deployment docs record the new provider settings and the threshold and margin, and the note that the production frontend flag is enabled by a rebuild once this is live and checked.

**Key interfaces:**
- The existing match service and DTOs from ticket 02, backed by the embeddings repository and provider boundary from ticket 05.
- Configuration for threshold, margin and provider, with defaults and validation at startup.
- Regenerate `openapi.json`; the diff should show no schema change, which is the check that the contract held.

**Acceptance criteria:**
- [ ] With the provider faked and stored embeddings in real Postgres, a photo whose embedding is closest to one Card by a clear margin returns that Card with `confident: true`
- [ ] A near-tie returns both Cards as candidates with `confident: false`; a weak top score returns `confident: false`
- [ ] A Card without an embedding never appears in results, and results only come from the current model's embeddings
- [ ] A provider error or timeout returns a classified error with no provider internals
- [ ] The random stub is gone and `openapi.json` is unchanged
- [ ] A manual check with the real provider against the seeded Expansion Set from ticket 05 returns the right Card for a real photo
- [ ] `go build ./...`, `go vet ./...`, `gofmt -l .` and `go test ./...` pass

**Out of scope:**
- Any frontend change, including turning on the production flag
- OCR or hybrid matching, unless ticket 01's report chose it as the fallback, in which case split it into its own ticket first
- Server-side card detection, foreign print editions, and Phase 2 binder-page scanning
