# 03: Scan a card into a Draft Addition (frontend)

**Category:** enhancement
**Status:** resolved

**Blocked by:** 02 (scan API contract: `cardId` filter and live stub match endpoint)

Spec: `.scratch/card-scanning/spec.md`. Glossary: Draft Addition.

## Agent Brief

**Category:** enhancement
**Summary:** From a Collection, the user can scan Cards with the camera (or a photo file), and each match lands in a Draft Addition shown as a tray with editable quantities. Frontend only, built against the stub endpoint. Reviewing and committing the draft is ticket 04.

**Current behavior:**
A Collection's page has no way to add Cards from a photo. There is no scan screen, no draft, and no camera code.

**Desired behavior:**
1. **Feature flag.** A build-time `VITE_*` environment variable enables the feature. When it is off (the default for production), the "Scan cards" button and the scan route do not appear. The flag is documented where the other `VITE_*` variables are.
2. **Entry.** A signed-in user sees a "Scan cards" button on a Collection's page, which opens a scan screen scoped to that Collection. A Guest never sees it.
3. **Capture.** The scan screen shows a live camera viewfinder with a card-shaped guide and a capture button. On capture the browser crops to the guide, downsizes to about 1024 pixels on the long side, and uploads a JPEG to the match endpoint. When the camera is unavailable, denied, or on a desktop, a file picker feeds the same crop, resize and upload path, and a clear message explains a denied permission.
4. **Match handling.** A confident match adds one copy of that Card to the draft and briefly shows the matched card (image, name, Expansion Set, card number) with an undo. A non-confident result shows the candidate cards, and the user taps one to add it or skips. A failed or slow match request shows a clear message and leaves the draft untouched.
5. **Draft.** The draft is a list of (card id, quantity to add) for this Collection. Scanning the same Card again raises its quantity, so duplicates merge into one row. A tray shows each row with the Card's image and name and controls to raise, lower or remove it, plus a way to discard the whole draft. Quantities mean additions to what the Collection already holds, not totals.
6. **Persistence.** The draft is held in memory and mirrored to local browser storage per Collection, so it survives a refresh, a tab discard, or the phone switching apps. It stores only ids and quantities; the tray renders each row by fetching Cards by id with the new catalog `cardId` filter. A draft whose Collection fails to load as missing is dropped quietly.
7. **Navigation.** A "Review and add" button is present, wired to a placeholder that ticket 04 replaces.

**Key interfaces:**
- The generated API client from the regenerated `openapi.json` (match route, catalog search with `cardId`).
- A frame source boundary that yields a JPEG from the camera or the file picker, so tests can fake it.
- A draft store keyed per Collection, with local-storage mirroring.
- Follow the frontend conventions for routes, data fetching and tests, and the accessibility rules already applied to the catalog grid.

**Acceptance criteria:**
- [x] With the flag off, the button and route are absent; with it on, signed-in users see the button on a Collection's page
- [x] A capture (camera or file picker) uploads a cropped, downsized JPEG and shows the match result
- [x] A confident match adds one copy to the tray with an undo; a non-confident result offers candidates to pick or skip
- [x] Scanning the same Card twice shows quantity 2 in one row; quantities can be raised, lowered and removed; the draft can be discarded
- [x] A reload restores the draft for that Collection, shows its Cards through the `cardId` filter, and a second Collection has its own separate draft
- [x] A denied or missing camera shows a clear message and the file picker still works; a failed match request shows a message and keeps the draft
- [x] Feature tests render the scan route with the generated client mocked and a faked frame source; the project's verification scripts pass

**Out of scope:**
- Reviewing and committing the draft (ticket 04)
- Live auto-capture from video, and server-side card detection
- The real matcher (tickets 05 and 06) and any backend change
- A scan-screen privacy notice

## Answer

Implemented on `feat/card-scanning-frontend` (merged into `feat/card-scanning`). The flag is `VITE_SCAN_ENABLED` (exactly `true` turns it on), documented in `frontend/.env.example` and `docs/agents/deployment.md`.
