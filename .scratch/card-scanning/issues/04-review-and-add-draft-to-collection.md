# 04: Review and add the draft to the Collection (frontend)

**Category:** enhancement
**Status:** resolved

**Blocked by:** 03 (scan a card into a Draft Addition)

Spec: `.scratch/card-scanning/spec.md`. Related: ticket 20 of the MVP issues (the bulk update endpoint).

## Agent Brief

**Category:** enhancement
**Summary:** The user reviews their Draft Addition and adds it to the Collection in one action, with clear handling of the cards the Collection cannot take. Frontend only, using the existing bulk update. This ticket also adds the end-to-end spec for the whole flow.

**Current behavior:**
After ticket 03, a draft can be built but the "Review and add" button leads nowhere, so scanned Cards never reach the Collection.

**Desired behavior:**
1. **Review step.** "Review and add" lists every row with the Card, the quantity being added, and how many copies the Collection already holds. Quantities can still be edited or rows removed here. A running total of the Collection's cards against its capacity limit (when one is set) is shown as a warning only.
2. **Commit.** Pressing "Add to Collection" reads the Collection's current quantity for each draft Card with the existing Collection entries lookup (card id filter, at most 100 ids per request, so batch larger drafts), computes an absolute target per Card as current plus added, and sends the existing bulk update. The bulk update is idempotent on retry.
3. **Result handling.** Rows reported as applied leave the draft. Rows reported as declined (over capacity, or a Card the server does not know) stay in the draft with their reason shown and can be fixed or dropped. The whole draft is cleared, and the user returns to the Collection's page, only when nothing was declined. A request failure keeps the draft intact and shows a message.
4. **Fresh quantities.** The Collection's cached lists and quantities are refreshed after a commit, so the Collection's page shows the new totals.
5. **End-to-end.** One Playwright spec, signed in through the existing Clerk e2e setup, drives the file-picker path with a stubbed match response: scan, review, add into a seeded Collection, and see the new quantity on the Collection's page. It needs no camera.

**Key interfaces:**
- The generated client's Collection entries search and bulk update calls, and the draft store from ticket 03.
- Reuse the quantity-batching and cache-patching patterns already used when adding Cards from the catalog, where they fit.
- Follow the signed-in e2e conventions (the signed-in tag and untraced project) described in the testing docs.

**Acceptance criteria:**
- [x] Review lists all rows with added and already-held quantities, and edits made here are respected on commit
- [x] The commit sends absolute targets (current plus added), batching the quantity lookup at 100 ids, and a retry does not double-add
- [x] Applied rows leave the draft; declined rows stay with their reason; a fully applied draft clears and returns to the Collection's page
- [x] A request failure keeps the draft and shows a message
- [x] The capacity running total is shown and does not block the request; the server decides
- [x] The Collection's page shows updated quantities after a commit
- [x] Feature tests cover mixed applied and declined results; the Playwright spec passes for the scan, review and add flow; the project's verification scripts pass

**Out of scope:**
- Any backend change; if the bulk update needs changing, raise it instead of changing it here
- Cross-Collection adds and Master Inventory changes
- The real matcher (tickets 05 and 06)
