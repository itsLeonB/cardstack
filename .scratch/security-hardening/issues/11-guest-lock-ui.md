# 11: Guest lock UI

**Parent:** `.scratch/security-hardening/spec.md`

**What to build:** The catalog UI mirrors the API's guest lock. A Guest sees locked controls that explain themselves and a clear prompt where more results would load, and signing in from any prompt brings them back to the same catalog view. A signed-in user sees no change.

**Blocked by:** 08, 10.

**Status:** done

- [x] For a Guest, the rarity, category and tag filter controls are visible but disabled with a "Sign in to use filters" prompt. Name search and Expansion Set browsing work normally.
- [x] For a Guest on an infinite grid (catalog search and Expansion Set page), the end of the first page shows "Sign in to see more" in place of the next-page load, and no request for page 2 is made.
- [x] For a Guest, Add to collection and quantity controls show a sign-in prompt instead of acting.
- [x] Any `login_required` response from the API is handled gracefully as a sign-in prompt, never as a generic error toast.
- [x] Signing in from any prompt returns the user to the same catalog view with their search intact (using the same-origin redirect rule).
- [x] The grid's accessibility behavior from the earlier infinite-scroll tickets still holds for the Guest prompt (keyboard reachable, announced).
- [x] Feature tests (generated client and Clerk hooks mocked) cover Guest and signed-in rendering and the return-after-sign-in behavior; frontend build, type check, lint and tests pass. Browser-level behavior is verified manually or by e2e, and the ticket says which.

## Comments

### Implementation notes

- **Guest state.** `useIsGuest()` (`lib/session.ts`) is true only once Clerk has loaded with nobody signed in. While Clerk loads nothing is locked, so a signed-in user never sees the lock flash up; a request made in that window carries the right token anyway (`customFetch` waits for Clerk). If clerk-js never loads, the UI stays unlocked and the API's `login_required` answer is what the user sees, as a prompt (below).
- **Filters.** `FacetFilters` takes `locked`: Rarity, Category and Tag triggers are disabled (`MultiSelect` gained `disabled`) and a "Sign in to use filters" link sits under them. Expansion Set stays open and name search is untouched. The facets endpoint is locked to a Guest, so the search page does not run the facets query for one (`enabled: !isGuest`) and fills the Expansion Set dropdown from the Series list instead (`guestFacets` in `lib/catalog-search.ts`). Chips for a locked filter that arrived in the address stay removable. The route loader still prefetches facets for everyone: gating it on `auth.isSignedIn()` would make a server-rendered direct load wait on Clerk, which does not exist there; a Guest's prefetch is a harmless unused 401.
- **End of the first page.** `InfiniteCardResults` takes `guest`: no scroll-triggered or button load, and "Sign in to see more" (a link styled like the Load more button) replaces the button. It lives in a live region that is always mounted, like the card-count line, so it is announced; it is a link, so the keyboard reaches it after the last tile as Load more is reached today. A Guest's page 1 reports `limit: 24`, so `hasNextPage` is true when there is more, and the prompt follows from that. No request for page 2 is made.
- **`login_required`.** `infinitePages` throws `LoginRequiredError` for a 401 whose `code` is `login_required` (the code, never the text), `useInfiniteCardResultsProps` exposes `loginRequired`, and the grid shows "Sign in to see these results" in place of the error alert, for a locked filter in a pasted link, or for a page 2 refused after all. There is no toast anywhere on this path. Facets answered with 401 are ignored.
- **Add to collection.** The picker was already disabled for a Guest with a login link; its copy is now "Sign in to add cards to a Collection" and it uses the shared `SignInLink`. Quantity controls only exist once a Collection is selected, which needs a session, so there is nothing further to lock.
- **Return after sign-in.** Every prompt is a `SignInLink` (`components/auth/sign-in-link.tsx`) with `redirect` set to the page's own `location.href`, dropped unless `isSameOriginPath` accepts it; the login page's own validation then applies as before. The Card page's "Sign in" prompt (`CardHoldings`) uses it too. TanStack writes array filters in its canonical form (`expansionSetId=["s1"]` encoded), so the redirect is the router's own href for the view, which parses back to the same filters.
- **Tests.** Unit: `infinite-pages` (`LoginRequiredError`, code not text), `infinite-catalog-cards`, `catalog-search` (`guestFacets`), `session` (`useIsGuest`), `facet-filters`, `infinite-card-results` (Guest prompt, never loads, live region, keyboard focus, `login_required`), `card-holdings`. Feature: `routes/catalog/-guest-lock.test.tsx` mounts the real search and Expansion Set route files with Clerk's hooks faked and `fetch` standing in for the API with its guest lock; it covers Guest and signed-in rendering, the request log (page 1 only, facets not used), `login_required` for a locked filter in the address, and following a prompt to the login page with the redirect intact.
- **Browser-level behavior: not verified here.** This sandbox's Chromium cannot trust the agent proxy's CA, so clerk-js never loads and the app never leaves its loading state; I did not bypass certificate checks. What is written but not run: the new guest spec `e2e/catalog-guest-lock.spec.ts` (disabled filters and prompt, "Sign in to see more" with page 1 only requested, the redirect it builds, axe, the Expansion Set page), and the existing specs the lock now breaks, converted to signed-in suites (`catalog-infinite-scroll.spec.ts` except its legacy `?page=` case, and the rarity, category and tag specs of `catalog-search.spec.ts`). The signed-in ones also need the Clerk test credentials, so the first CI run with them is the check; expect to adjust selectors or navigation if it finds any. One manual pass in a browser against the development instance (as a Guest: filters locked, prompt at the end of page 1, sign in from it and land on the same search; as a signed-in user: nothing changed) closes this.
