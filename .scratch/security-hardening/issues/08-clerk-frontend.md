# 08: Clerk frontend

**Parent:** `.scratch/security-hardening/spec.md` (see ADR-0015)

**What to build:** Sign-in and sign-up run on Clerk's prebuilt components, themed to the visual identity, at their current addresses. Every API call carries the Clerk token as a bearer header, and signed-in state across the shell, route guards and redirects comes from Clerk. A user can sign up with Google or email, verify, sign in, use the app and sign out.

**Blocked by:** 07, 01.

**Status:** done, except real-browser verification, which is deferred to ticket 09 (see Implementation notes)

- [x] The Clerk provider wraps the app, which stays an SPA (ADR-0014 is not reopened). Confirm Clerk's SDK for TanStack Start works in the app's SPA mode.
- [x] The sign-in and sign-up pages stay at their current addresses and render the prebuilt components themed for light and dark, keeping the noindex behavior those pages have today.
- [x] The shared request wrapper used by the generated client attaches the current token as a bearer header. On a 401 it requests a fresh token and retries once; a second 401 triggers the existing auth-lost handling.
- [x] The shell (header, user menu, sign-out), route guards and the redirect rules (return to the original page after sign-in, restricted to same-origin paths; signed-in users redirected away from guest-only pages) derive from Clerk. The name and email shown come from Clerk's user data.

## Comments

### Implementation notes

**SDK choice: `@clerk/react` (v6), not `@clerk/tanstack-react-start`.** The app is a TanStack Start app in SPA mode (`tanstackStart({ spa: { enabled: true } })`): Vercel serves a static `_shell.html` and there is no server at runtime. `@clerk/tanstack-react-start` is built around server-side auth: its docs require `clerkMiddleware()` in `src/start.ts` and its helpers (`auth()`, server functions) read request state, none of which exists here. `@clerk/react` is the plain React SDK (`ClerkProvider`, `useUser`, `useAuth`, `SignIn`, `SignUp`, and a standalone `getToken` that works outside React) and needs only the publishable key, so it fits ADR-0014's SPA unchanged. Confirmed against Clerk's docs through context7 and against the installed package; `bun run build` prerenders the shell with the provider in place, and in a headless Chromium against the dev server the provider mounted, requested clerk-js and the app degraded cleanly when Clerk could not be reached (see "Not verified"). If SSR is ever turned on, revisit this choice together with ADR-0014.

**Missing key.** `AppClerkProvider` (`components/auth/app-clerk-provider.tsx`) renders a plain `role="alert"` error instead of the app when `VITE_CLERK_PUBLISHABLE_KEY` is empty, so a misconfigured deploy cannot pass as a working guest site. The build still succeeds without the key (frontend CI has no secret requirement), unlike `VITE_SITE_URL`, which fails a Vercel production build; add the same check if a production deploy without the key should stop at build time.

**How the guards get Clerk state.** Guards run in `beforeLoad`, outside React, so the router context now carries `auth: AuthGate` (`lib/clerk-auth.ts`), injected in `getRouter()`. Its `isSignedIn()` calls Clerk's standalone `getToken()`, which waits for Clerk to finish loading (10 seconds, then it throws; that reads as signed out) and returns null exactly when nobody is signed in. A reload on a protected page therefore waits for Clerk instead of bouncing a signed-in user, and the guard reads Clerk's live state, so the navigation Clerk performs right after a sign-in sees the new session. `ClerkProvider` mounts while the first route is still loading, so the wait does not deadlock (observed in the browser). Layouts whose guard needs Clerk (`_authenticated`, `auth`) set `ssr: false`: the dev server renders a direct load on the server, where there is no Clerk to wait for. `requireAuth` and `requireGuest` keep their redirect rules; `isSameOriginPath` and `redirectSchema` are unchanged, and `redirectSearchSchema` (`{ redirect }`) is shared by login and register.

**How the token getter is wired.** `http.ts` exposes `setTokenGetter` (browser-only, like `setOnAuthLost`, so a server render can never leave a request's state in the singleton); `router.tsx` registers `getSessionToken` from `lib/clerk-auth.ts`. `customFetch` attaches `Authorization: Bearer <token>` when there is one and sends no header for a guest, with no `credentials` and no CSRF header. A 401 on a request that carried a token asks Clerk for a fresh token (`skipCache: true`, one shared request for concurrent 401s) and retries exactly once; a second 401, or Clerk answering that the session is gone (null), calls the auth-lost handler once per expiry (`rearmAuthLost` re-opens it when the Clerk session changes). A guest's 401 is never retried or reported, and neither is a 401 when Clerk cannot be reached for the fresh token. If Clerk cannot supply a token at all, the request goes out as a guest.

**Session state.** `useSession()` is now derived from `useUser()`: `{ user: { id, name, email } | null, isAuthenticated, isLoading }` (name from Clerk's full name, email from the primary address); the `query` field is gone. The header, user menu, account page and dashboard greeting read name and email from it. `SessionSync` (mounted inside `ClerkProvider`) watches Clerk's session id and, on a change after the first load (sign-in, sign-out, another account, or either in another tab), calls `handleSessionChange`: drop the whole query cache and re-arm the auth-lost notice. Sign-out is `useSignOut()` (`signOut({ redirectUrl: "/auth/login" })`, toast on failure) in both the user menu and the account page.

**Sign-in and sign-up.** `/auth/login` and `/auth/register` keep their addresses and render `<SignIn>` / `<SignUp>` with `routing="path"`. Clerk's sub-steps (`factor-one`, `verify-email-address`, `sso-callback`, ...) live beneath those paths, so each address is an index route plus a splat route (`login/index.tsx` and `login/$.tsx`, `register/index.tsx` and `register/$.tsx`); a single splat file would also match the bare path but would break the typed `to="/auth/login"` links. `vercel.json` already rewrites every path to the SPA shell and sets noindex on `/auth/:path*`, so no change was needed there. `forceRedirectUrl` is the validated `redirect` search param or `/account` (force, not fallback, so a `redirect_url` query param cannot pick the destination); the switch link between the two pages carries the `redirect` param. `pageHead(...)` and NOINDEX are unchanged, and `AuthPage` keeps a screen-reader-only `h1`. Theming is `lib/clerk-appearance.ts`: Clerk's `variables` point at the app's CSS variables (`var(--primary)`, `var(--card)`, ...), so the `.dark` class that `ThemeProvider` toggles themes Clerk too, with no theme state of its own. The `AuthShell` is unchanged. `ClerkProvider` gets `routerPush`/`routerReplace` backed by `router.history`, so Clerk's steps stay in the SPA.

**Removed.** Cookie and CSRF handling (`setCsrfToken`, the csrf cookie/sessionStorage logic, `credentials: "include"`), the refresh-on-401 flow, `useGetCurrentUser` and the whole generated auth client (regenerated with `bun run codegen`; the auth endpoints and `MeResponse` are gone from the spec), the login/register mutation hooks, the old login and register forms with `-login.test.tsx` and `-register.test.tsx`, `AuthField`, and the `registered` search param. `src/generated/**` was regenerated, not edited.

**Tests.** `lib/http.test.ts` (bearer present for signed-in, absent for guest, fresh token and one retry, second 401 reports once, no retry or report for a guest, shared fresh-token request, server-realm registrations ignored), `lib/route-guard.test.ts` (guards wait for Clerk; redirect target and query string), `lib/clerk-auth.test.ts`, `lib/session.test.tsx`, `lib/auth-lost.test.ts`, `components/auth/session-sync.test.tsx` and `app-clerk-provider.test.tsx` (missing key fails loudly, provider props, router navigation), `components/layout/user-menu.test.tsx` and `site-header.test.tsx` (guest versus signed-in shell, name and email, sign-out and its failure toast), `home-page.test.tsx` (greeting), and `routes/-auth-flow.test.tsx` through the real route files with Clerk's hooks and components faked (guest to a protected page lands on login with the redirect param; an off-origin redirect is rejected; a signed-in user is sent away from login, register and their steps; Clerk still loading neither redirects nor renders; splat steps are served; noindex and `pageHead` kept). Clerk's hooks and the generated client are mocked at the module boundary; no test reaches Clerk.

**Pipeline.** `VITE_CLERK_PUBLISHABLE_KEY` was already in `frontend/.env.example` (ticket 01); `docs/agents/deployment.md` now documents it (Production only on Vercel, production instance, owner-controlled domain; preview, CI and local use the development instance). The frontend CI build and the end-to-end Playwright step read it from the GitHub variable of the same name, and the preview workflow adds it as a branch-scoped Vercel env var next to `VITE_API_BASE_URL` and deletes both when the PR closes (the Vercel project's own value is Production-only, per `scripts/clerk-setup.sh`). `docs/agents/conventions/frontend.md` bullets about `useSession` and `resetCache` were rewritten for the new mechanics.

**End-to-end specs.** Specs that simulated a session by stubbing `/auth/me` (signed-in suites in `app-shell`, `home`, `not-found`, `seo`, `inventory-infinite-scroll`) and the ones that used the old forms (login redirects, signed-in redirect away from auth pages) are `test.fixme` with a pointer to ticket 09; the field-error and password-toggle specs of the removed forms were deleted. Guest specs that need no sign-in stay active; `auth.spec.ts` gained a guest-to-login redirect spec, and `catalog-infinite-scroll.spec.ts` lost a dead `/auth/me` stub. Ticket 09 owns the Clerk Testing Tokens layer and should turn the `fixme`s back on.

**Not verified in a real browser (deferred to ticket 09, and worth one manual pass by the owner against the development instance).** I had no reachable Clerk instance, so none of this has run against real Clerk: the prebuilt `<SignIn>` / `<SignUp>` rendering, their look in light and dark (the CSS-variable mapping in `clerk-appearance.ts`, and whether Clerk's colour derivation from oklch variables looks right), Google sign-in and the email code step, Clerk's own redirects, sub-step navigation under the splat routes, the post-sign-in return to the original page, sign-out from a real session, a real expired token followed by the retry, and axe on the Clerk-rendered pages (the active auth e2e specs run axe and assert a visible `h1`; they have not been run). Clerk's own header may itself be an `h1`, which would leave two on those pages. What was checked in headless Chromium against the dev server with a placeholder key: the provider mounts and requests clerk-js while the first guard is still waiting (no deadlock), and with Clerk unreachable a guarded route redirects to login with the `redirect` param after the 10 second wait.

**Known limitations for the reviewer.** (1) With Clerk unreachable (blocked script, outage) every call to Clerk's `getToken` waits 10 seconds before failing, so public API calls and guarded navigations are delayed that long and then proceed as a guest; a memo of the failure would shorten that and was left out as scope. (2) When the second 401 is real (a valid Clerk session the API rejects, for example an authorized-party mismatch), the auth-lost redirect to login is bounced to `/` by `requireGuest` because Clerk still reports a session, so the user sees the toast and a signed-in header; the app does not sign the user out of Clerk in that case. (3) `getToken()` doubles as the guards' "is anyone signed in" probe, which also warms Clerk's token cache.
