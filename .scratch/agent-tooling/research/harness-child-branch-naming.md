# Naming and discovering a worker's branch and worktree across harnesses

Question: `docs/agents/orchestration.md` (Big task, step 3) wants each worker on `<type>/<feature>-<component>`, created from the feature branch. ### What a worker's `git branch -m` breaks in T3

T3's own rename is `git branch -m` run in the worktree, so git-wise the operation is the same one T3 performs. The risk is T3's stored copy of the name.

- Nothing syncs git `HEAD` back into a server thread. Every server-side `thread.metadata.update` dispatch that sets a branch is launch preparation (workspace record, background rename, cancelled-setup reset) or the handoff (`ThreadLaunchService.ts:466`, `:498`, `:526`, `:687`; `WorktreeMcpService.ts:280`). The others set a title, an empty-claim flag or usage-limit state (`ThreadLaunchService.ts:900`, `UsageLimitRecoveryWorker.ts:39`, `Orchestrator.ts:13560`, `ThreadMetadataMcpService.ts`). The only live branch sync in the web app is for draft threads and is skipped once a server thread exists (`apps/web/src/components/GitActionsControl.tsx:1070-1087`). A manual rename in the UI branch selector writes it (`BranchToolbarBranchSelector.tsx:172-200`). Verified (source) that no automatic writer syncs from git; I grepped every `thread.metadata.update` call site and read the non-launch ones except `ThreadMetadataMcpService.ts`, whose `thread_update` tool description says "Workspace and branch cannot change here" (`orchestrator/tools.ts`, `ThreadUpdateTool`).
- T3's own rename is guarded with `expectedBranch`, so if the worker renamed first, T3's `git branch -m -- <old> <new>` fails on a missing old name, the failure is only logged ("Thread worktree branch rename failed"), and `thread.branch` stays `t3/<hex>` (`ThreadLaunchService.ts:497-547`, catch at `:549-552`). If T3 renames first, the worker's own rename must use the current-branch form `git branch -m <new>`, not `git branch -m <old> <new>` with the old temporary name, or it fails. Inferred from the code ordering; the two rename calls run concurrently with the agent start and I did not observe the race.
- Where a stale `thread.branch` is read:
  - Pull-request lookup and settlement call `git.branchPullRequest({ cwd, branch: thread.branch })` (`apps/server/src/orchestration-v2/ThreadSettlementService.ts:478-483`, `:493-499`), so a renamed branch would not be matched to its PR automatically. Verified (source) that the stale name is used; the user-visible effect (a thread not auto-settling) is inferred.
  - Resume after storage cleanup removed the worktree: `ProviderTurnStartService` recreates a missing managed worktree from `thread.branch`. If that local branch name is not found it creates a **new** branch of that name from the project's current branch (`apps/server/src/orchestration-v2/ProviderTurnStartService.ts:163-185`, `:570-615`; cleanup comment at `apps/server/src/storageCleanup.ts:1042`). With a renamed branch that is a silent fresh branch with the old name. Verified (source) for the code path; it only triggers when the worktree directory is gone.
- Not broken by a rename: worktree removal during storage cleanup is by path (`storageCleanup.ts:1031-1038`), and explicit PR links are made by URL through `link_pull_request` (`apps/server/src/mcp/toolkits/pullRequests/handlers.ts`, no branch use found). Verified (source) by reading; the thread-delete path is inferred to be the same removal.
- Nothing in T3 refreshes the path when the branch is renamed; the path itself does not change, so the path is the stable key.

## 4. Plain git (git 2.43.0, run in `/tmp/rs-git`)

- `git branch -m <new>` inside a linked worktree renames that worktree's checked-out branch. The worktree's `HEAD` follows (`## feat/users-management-backend` after renaming `t3/bfbef076`), the main checkout's `HEAD` and status are unchanged, and the branch's commits keep their hash. Verified (run).
- The rename from the **main** checkout also works while the branch is checked out in a linked worktree: `git branch -m feat/users-management-backend feat/x-backend` run in main updated the linked worktree's `HEAD`, and `git worktree list --porcelain` showed `branch refs/heads/feat/x-backend` for it. So the orchestrator can rename after the fact without the worker's help. Verified (run). The worker's running tools see the new name on their next git call.
- `git worktree list --porcelain` reports one stanza per worktree (`worktree <path>`, `HEAD <sha>`, `branch refs/heads/<name>` or `detached`, plus `locked`/`prunable` lines), always the live branch, so it reflects a rename immediately (git-worktree(1) "LIST OUTPUT FORMAT"; Verified (run)). `merge-ticket` already reads this format and its exact `branch refs/heads/<branch>` match works after a rename as long as it is given the new name. Verified (run) for the match; I read `main.go:27-39`.
- Renaming onto an existing name is refused (`fatal: a branch named 'feat/x-backend' already exists`). Verified (run). The branch reflog records `Branch: renamed … to …`. Verified (run).
- Is `list --porcelain` enough for an orchestrator that knows only a thread id or a marker commit? **Not by itself.**
  - It lists every worktree, keyed by path and branch, and says nothing about which thread owns which. Before/after launch, a set difference of the path lists identifies a new worktree if only one was created in that window. Inferred; races with parallel launches.
  - A unique marker in a worker commit message is found with `git log --all --grep=<marker> --format='%H %D'` or `git for-each-ref --contains <sha> refs/heads` and then mapped to a path by matching the branch in the porcelain output. I ran this and it returned the renamed branch. Verified (run). It only works after the worker has committed.
  - The stable join key is the **path**. T3 gives the path via `t3_thread_read` (`thread.worktreePath`), Claude Code via `worktreePath` in the Agent result, and the path does not change on rename (T3 docs above; git: the directory is untouched, Verified (run)). Then `git -C <path> symbolic-ref --short HEAD` returns the live branch. Verified (run) for the git side.
  - A removed directory shows up as `prunable` until `git worktree prune`; a detached worktree has no `branch` line, so the exact-match in `merge-ticket` would miss it (`prunable` and `(detached HEAD)` shown in my run). Verified (run).

## Recommendation

Make the **name a request, not a requirement**, and make the **path the contract**.

1. In `orchestration.md`, say that the orchestrator records the worker's worktree path from the harness and reads the real branch with `git -C <path> symbolic-ref --short HEAD` (or the matching stanza of `git worktree list --porcelain`), and passes that exact branch to `merge-ticket merge` and `cleanup`. This works for every harness in section 1-4 that creates a git worktree, and it survives a rename by anyone.
2. Where the harness lets the caller choose the name up front, ask for `<type>/<feature>-<component>`: in T3 that is `t3_thread_launch` with `workspaceStrategy.branch`, and with plain git `git worktree add -b`. Do not ask the worker to rename (option C); it races T3's own rename and leaves T3's stored branch stale.
3. For `delegate_task` with `isolation:"worktree"`, accept `t3/…` and discover it. Do not try to steer it with project settings (option E).
4. If the maintainer wants the convention enforced for a harness that cannot take a name, rename from the orchestrator after the worker reports done (option D), knowing T3's stored `thread.branch` will be stale for PR matching and resume.
5. Small follow-up that would make this robust (not done here, per the brief): `merge-ticket` could accept `--worktree <path>` and resolve the branch itself, and treat `detached` stanzas as an error.

Open items I could not settle from source or docs: the exact Claude Code subagent branch format (only observed once), what Cursor names its subagent branches, whether a T3 child that renames its branch concurrently with T3's background rename ends with a stale `thread.branch` in practice, and whether the installed T3 build matches commit `305a90d`.
