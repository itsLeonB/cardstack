## Q1. `t3_worktree_handoff` from a delegated child

**Precondition: the child inherits the parent's worktree.** `makeSubagentChildThread` copies the parent thread record (`...input.parentThread`), including `worktreePath` and `branch` (`apps/server/src/orchestration-v2/SubagentProjection.ts:42-85`). A handoff fails with `already_in_worktree` when the thread already has a `worktreePath` (`apps/server/src/mcp/WorktreeMcpService.ts:155-158`). So a delegated child can only hand off when its parent thread sits on the project root.

**Capability is not a blocker.** Every thread provider session gets `orchestration`, `worktree` and `pull-requests`, with no special case for subagent threads (`apps/server/src/orchestration-v2/ProviderSessionManager.ts:462-468`, `apps/server/src/mcp/McpSessionRegistry.ts:139-145`). The handoff checks only that capability plus a thread scope (`apps/server/src/mcp/WorktreeMcpService.ts:74-89`).

**The provider process restarts with cwd = the worktree.**
- The handoff dispatches `thread.metadata.update` with the new `worktreePath` and `branch` (`apps/server/src/mcp/WorktreeMcpService.ts:320-328`).
- A `thread.metadata.update` that changes `worktreePath` detaches every provider session on the thread, with reason "Workspace changed." (`apps/server/src/orchestration-v2/Orchestrator.ts:3275-3338`).
- Claude allows only one provider thread per session (`supportsMultipleProviderThreadsPerSession: false`, `apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts:179-181`). A detach that leaves no threads attached therefore releases the whole session (`apps/server/src/orchestration-v2/ProviderSessionManager.ts:2044-2058`).
- The next run resolves `cwd = thread.worktreePath ?? project.workspaceRoot` (`apps/server/src/orchestration-v2/RuntimePolicy.ts:106-134`).
- That cwd becomes the Claude Agent SDK `cwd` option and an `additionalDirectories` entry (`apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts:805-924` and `:7110-7135`).

**The continuation is queued before the old turn dies.**
- `continuationPrompt` is sent with `mode: "queue"` right after the binding commits (`apps/server/src/mcp/WorktreeMcpService.ts:357-392`).
- The code comment says: "When the dying run reaches a terminal state the orchestrator promotes the queued run, which derives its cwd from the updated projection" (`:357-362`).
- Unverified: how the resumed session finds the old transcript after the cwd change. "Conversation preserved" is T3's own claim (`apps/server/src/mcp/WorktreeMcpService.ts:437`). I found no code that relocates the transcript. Observed: after the handoff, the probe's run 3 followed the TURN 2 steps from its original prompt, so the conversation did carry over.

**The child stays linked to the parent.** The handoff changes only `branch` and `worktreePath`. It does not touch `lineage` (`parentThreadId`, `relationshipToParent: "subagent"`) or `forkedFrom`, which finalization relies on (`apps/server/src/orchestration-v2/SubagentProjection.ts:66-74`, `apps/server/src/orchestration-v2/Orchestrator.ts:9287-9293`).

**The parent is notified after the continuation turn, not after the first turn.** This is derived from code. I found no end-to-end test of handoff inside a delegated child.
- `delegatedTaskProgress` reports `working` while any non-monitor run in the child thread is non-terminal. A queued continuation run counts. `resultRun` is the most recent terminal run (`apps/server/src/orchestration-v2/SubagentProjection.ts:209-258`).
- `finalizeAppOwnedSubagent` returns early unless the state is `result_available` (`apps/server/src/orchestration-v2/Orchestrator.ts:9295-9296`). Only after that check does it publish the result and plan the parent wake (`planDelegatedCompletionDelivery` call at `:9380`).
- Finalization runs again on every terminal run event in any app-owned subagent thread, not only the spawning run (`handleTerminalRun`, `apps/server/src/orchestration-v2/Orchestrator.ts:10309-10320`). So when the continuation run ends, the task is re-checked and published.
- So the task `summary` is the last assistant message of the continuation run (`subagentResultForRun`, `apps/server/src/orchestration-v2/SubagentProjection.ts:158-208`).
- Without `continuationPrompt`, nothing is queued. The task would finalize when the detached first run ends, with whatever terminal status that run gets. Unverified: the exact run status for a detached run (session release maps runtime requests to `cancelled`, `apps/server/src/orchestration-v2/ProviderSessionManager.ts:244-248`, but I did not trace the run status). Observed with `continuationPrompt` set: the detached run 1 ended as `failed` ("provider event stream closed unexpectedly").

**What `latestTerminal*` and `hasPendingChildRuns` are for.**
- `hasPendingChildRuns`: true when the child thread has a non-terminal run with a higher ordinal than the original delegated run (`apps/server/src/mcp/OrchestratorMcpService.ts:356-365`). The tool text says it "reports later queued or executing turns in the backing child thread, even after the task is terminal; it does not reopen the task" (`apps/server/src/mcp/toolkits/orchestrator/tools.ts:76`).
- `latestTerminal*`: the newest terminal, non-monitor, non-rolled-back run in the child thread (`apps/server/src/mcp/OrchestratorMcpService.ts:436-455`, `:1284-1294`). It exposes results of turns that ran after the published task result, without replacing `summary` (`docs/orchestration-v2/orchestrator-mcp-server.md:271-278`).
- In the handoff case, the continuation finishes before the task is published, so `summary` already holds its result. These fields matter for runs that happen after publication, such as a later `t3_thread_send` to the child thread.

## Q2. How the delegated-task completion reaches the parent

**Wake policy depends on mode.** `mode: "async"` sets `completionWake: "always"`. `mode: "wait"` sets `"settled_only"`, and the policy is upgraded to `always` only if the wait times out (`apps/server/src/mcp/OrchestratorMcpService.ts:1766-1769`, `:1797-1840`). `settled_only` offers a wake only when the parent has no live run (`apps/server/src/orchestration-v2/Orchestrator.ts:9118-9130`, `packages/contracts/src/orchestrationV2.ts:678-683`).

**Delivery is a server message.** The continuation worker dispatches a server-created `message.dispatch` with `dispatchMode: queue_after_active`. Its text is "Delegated task <id> reached a terminal state. Use task_status with taskId <id> to read the result." (`apps/server/src/orchestration-v2/ProviderContinuationService.ts:13-18`, `:115-146`).

**Steer vs queue for a Claude parent: always a queued new turn.**
- The orchestrator upgrades delivery to `steer_active` only when every task is `always`, the parent has a running turn, and the session has `supportsActiveSteering && activeSteeringInterruptsTools !== true` (`apps/server/src/orchestration-v2/Orchestrator.ts:4644-4677`). The code comment reads: "Never interrupt/restart a turn for a notification."
- Claude declares `activeSteeringInterruptsTools: true` (`apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts:201-202`). So for a Claude parent, the completion is always queued as a new turn after the active run, or started immediately if the parent is idle.
- The tool description's "steered into active turns where supported" (`apps/server/src/mcp/toolkits/orchestrator/tools.ts:63`) applies to other providers only.

**Limits:**
- Reading a terminal result with `task_status`, or getting it through `delegate_task` wait, acknowledges the automatic delivery and suppresses the wake (`apps/server/src/mcp/OrchestratorMcpService.ts:1297-1310`, `apps/server/src/mcp/toolkits/orchestrator/tools.ts:76`).
- Sibling completions are batched into one queued delivery message while it is still queued (`apps/server/src/orchestration-v2/Orchestrator.ts:9136-9170`).
- Delivery is disposed when the parent thread is archived or deleted, or its cohort is closed (`apps/server/src/orchestration-v2/Orchestrator.ts:9098-9116`). `task_cancel` also disposes it (`docs/orchestration-v2/orchestrator-mcp-server.md:280-288`).
- The wake carries only task IDs. The parent must call `task_status` to read the result (`apps/server/src/orchestration-v2/ProviderContinuationService.ts:13-18`).
- A failed dispatch is retried with exponential backoff capped at 5 s (`:75-81`, `:183-226`).

## Q3. Notification for a `t3_thread_launch` thread

**There is no automatic completion notification.**
- Launched threads are "ordinary top-level" threads with no subagent lineage (`docs/orchestration-v2/orchestrator-mcp-server.md:311-330`, `apps/server/src/mcp/toolkits/project/tools.ts:104-105`).
- The only completion-to-parent path, `finalizeAppOwnedSubagent`, returns immediately unless `relationshipToParent === "subagent"` (`apps/server/src/orchestration-v2/Orchestrator.ts:9287-9293`).
- The launcher's thread ID is stored on the first message as `senderThreadId` (`apps/server/src/mcp/toolkits/project/handlers.ts:107-125`). Its schema comment says it records provenance: "The sending agent's thread in this environment" (`packages/contracts/src/orchestrationV2.ts:1116-1117`). I found no code that wakes the sender or puts the sender ID into the child's prompt.

**Supported options.**
- The launcher can poll or block with `t3_thread_wait` / `t3_thread_read`, which the docs recommend (`apps/server/src/provider/T3OrchestrationInstructions.ts:27`).
- The child can call `t3_thread_send` to the parent. Any thread is a valid target, as long as the target's modes are not broader than the caller's (`docs/orchestration-v2/orchestrator-mcp-server.md:369-382`, `:438-442`). The parent's thread ID has to be passed in the launch `message`. Observed: `orchestrator_capabilities` returns the caller's own thread ID as `parentThreadId`, and the orchestrator puts that ID into the launch message. `t3_thread_wait` on the child is safe for the parent to use: it "does not acknowledge a delegated result" (`apps/server/src/mcp/toolkits/orchestrator/tools.ts:232`).

**`mode=queue` on an idle parent starts a turn immediately.**
- `queue` maps to `queue_after_active` (`apps/server/src/orchestration-v2/ThreadManagementService.ts:554-576`).
- The orchestrator queues only when a blocking run is active (`apps/server/src/orchestration-v2/Orchestrator.ts:4768-4774`). Otherwise the message starts a run, and the result reports `delivery: "started"` (`apps/server/src/orchestration-v2/ThreadManagementService.ts:622-629`).
- If the parent is busy, the message waits behind the active run as a separate turn.
- Prefer `queue` over `auto` for Claude parents. `auto` steers into an active turn (`ThreadManagementService.ts:570-571`), and Claude steering interrupts tools (`activeSteeringInterruptsTools: true`).

## Q4. Working directory and project MCP servers for a worktree-bound thread

**cwd.** The Claude process gets `cwd = thread.worktreePath` when the thread is bound to a worktree, otherwise `project.workspaceRoot` (`apps/server/src/orchestration-v2/RuntimePolicy.ts:106-134`). That value is passed as the SDK `cwd` (`apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts:918-924`). `t3_thread_launch` binds the workspace "before the agent starts" (`docs/orchestration-v2/orchestrator-mcp-server.md:318-323`).

**One Claude process per thread.** Each thread has its own Claude session (`supportsMultipleProviderThreadsPerSession: false`, `ClaudeAdapterV2.ts:179-181`), and so its own Claude Code process.

**Project `.mcp.json` servers load from that cwd.**
- T3 passes only its own `t3-code` HTTP server in `mcpServers` (`ClaudeAdapterV2.ts:966-993`). It sets neither `settingSources` nor `strictMcpConfig`; neither appears anywhere in the Claude adapter (grep across `apps/server/src`).
- Claude docs: when `settingSources` is omitted, `query()` "loads the same filesystem settings as the Claude Code CLI: user, project, and local". `strictMcpConfig` defaults to `false`, and only `true` ignores project `.mcp.json` (https://code.claude.com/docs/en/agent-sdk/typescript, Options table).
- Claude docs: in Agent SDK sessions, Claude Code "can't show that prompt: it loads project-scoped servers without asking" (https://code.claude.com/docs/en/mcp, project scope section).
- This repo's `.mcp.json` is git-tracked, so every worktree has its own copy. Its Serena entry uses `--project-from-cwd`, so a per-thread Serena should be rooted at the worktree.
- Observed in this session (a T3-launched Claude process): `postgres` and `postgres-prod` were reported as failing to connect and `mcp__serena__*` tools are present. All three are defined only in this repo's `.mcp.json`; `~/.claude.json` defines no `postgres*` server and its `serena` entry is scoped to a different project. So project `.mcp.json` servers do start for T3 threads.
- Unverified: whether Claude Code resolves the project root as cwd or as the git top level. It does not matter here, because the worktree's top level is the worktree itself.
- Config-dependent: user-supplied Claude `launchArgs` are forwarded as `extraArgs` (`ClaudeAdapterV2.ts:832-836`, `:916`). A `--strict-mcp-config` or `--setting-sources` flag there would change this.

## Q5. Can `delegate_task` bind a child to a worktree?

No. `delegate_task` has no workspace parameter. Its input is `task`, `target`, `title`, `role`, `mode`, `timeoutMs`, `clientRequestId`, `runtimeMode` and `interactionMode` (`packages/contracts/src/orchestratorMcp.ts:170-191`).

The child always inherits the parent's workspace binding (`apps/server/src/orchestration-v2/SubagentProjection.ts:54-56`). There are two ways to get a child into a different worktree:

- Run the parent itself in a worktree, so the child shares it.
- Have a child whose parent is at root call `t3_worktree_handoff` with `continuationPrompt`. The handoff "moves the calling thread, not another thread" (`apps/server/src/provider/T3OrchestrationInstructions.ts:25`).

`t3_thread_launch` with `workspaceStrategy` is the only explicit bind-at-start option, and it creates a top-level thread with no parent link (`apps/server/src/mcp/toolkits/project/tools.ts:102-123`).

## Upstream issues behind the docs' rules

All on `pingdotgg/t3code`. The workflow docs state the rule, not the issue number, so recheck these when T3 updates and relax the rule if the issue is fixed.

- #15136: a child dies after a worktree handoff. Explains the failed handoff probe above and the stuck task. Rule: component work is launched with `t3_thread_launch` into a new worktree, never handed off from a delegated child.
- #15135: a thread that archives itself fails its own run. Rule: a component agent never archives its own thread, and the orchestrator archives it after merge.
- #15173: the idle release can fire while a parent waits on a delegated child. Rule: the orchestrator polls each launched child with `t3_thread_wait` and a 30-minute timeout instead of one long delegated wait. Whether a long wait trips it is an open assumption below.
- #13490: no parent notification for follow-up turns of a child. Rule: the orchestrator launches and polls children, and each child sends its own report by queued message.
- #15082: no parent notification when a delegated task asks a question. Rule: component work is not delegated with `delegate_task`; a child asks the orchestrator by queued message and ends its turn.
