## Agent Brief

**Category:** enhancement
**Summary:** Investigate whether and how the card lists (catalog search and the Collection detail page) can load more cards as the user scrolls to the bottom, using offset-based pagination on the API and TanStack Virtual on the client, and recommend an approach.

**Current behavior:**
The catalog search endpoint is already offset based (`page`, `limit` and a `total` in the response metadata), and the frontend shows numbered page controls. There is no infinite scroll and no list virtualization.

**Desired behavior:**
A short research document that answers, with primary-source evidence (TanStack Virtual, TanStack Query and TanStack Router documentation, and a small throwaway prototype where it settles a question):
- How to combine TanStack Query's infinite query with the existing page and limit parameters, and how to detect "scrolled near the bottom" with TanStack Virtual.
- How to virtualize a responsive grid of card tiles (rows of variable column count) rather than a single-column list.
- How infinite scroll interacts with filters kept in URL search params: resetting on filter change, scroll restoration on back navigation, and linkable state.
- Offset pitfalls: duplicated or skipped cards when the underlying data changes between page fetches, and whether the API needs a stable secondary sort.
- Interaction with the +/- quantity controls and pending debounced edits from tickets 22 and 23, and with facet updates from ticket 21.
- Accessibility (keyboard, screen reader, a fallback "load more" control) and test strategy.
- A recommendation with the smallest workable design and an estimate of what tickets it would split into.

**Key interfaces:**
- The existing catalog search and Collection entries list contracts: `page`, `limit`, `total`.
- The shared card grid component from ticket 22, if it exists by then; otherwise the current catalog results component.
