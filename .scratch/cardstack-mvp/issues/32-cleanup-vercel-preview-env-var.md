# 32: PR cleanup leaves a VITE_API_BASE_URL entry behind in Vercel for every PR

**Category:** enhancement
**Status:** ready-for-agent

**Blocked by:** None (can start immediately)

## Agent Brief

**Category:** enhancement
**Summary:** The preview-environments workflow adds a branch-scoped `VITE_API_BASE_URL` env var to the Vercel project for every PR, but the `cleanup` job (run on PR close/merge) never removes it, so the project accumulates one stale entry per PR. Make `cleanup` delete that PR's entry.

**Current behavior:**
- `provision` runs `vercel env add VITE_API_BASE_URL preview "$HEAD_REF" --force` in the "Point this PR's Vercel preview at the Railway API" step of `.github/workflows/preview-environments.yml`. This creates a Vercel env var scoped to the `preview` target and the PR's git branch.
- `cleanup` ("Delete preview stack") deletes the Neon branch and this PR's Vercel preview deployments, but nothing removes the env var. The PR comment also claims everything is "Torn down automatically when this PR is merged or closed", which is not true for this entry.
- Confirmed by reading the workflow only; not reproduced against the live Vercel project.
- The maintainer has already manually cleared the existing stale entries, so no backfill is needed.

**Desired behavior:**
- When a PR is closed or merged, `cleanup` removes the `VITE_API_BASE_URL` entry scoped to `preview` and that PR's head branch, and only that one. Entries for other branches and for `production` or unscoped `preview` must be untouched.
- The step passes when no such entry exists (for example provisioning failed before the env var was added, or `cleanup` is re-run). It still fails on real errors (bad token, API failure) rather than swallowing them.

**Key interfaces:**
- `cleanup` job in `.github/workflows/preview-environments.yml`. Add the new step after "Delete this PR's Vercel preview deployments"; it needs the same `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID` and `HEAD_REF` env vars that step already sets.
- Preferred mechanism: the Vercel CLI, installed at the same pin `provision` uses (`npm install -g vercel@59.11.7`), running `vercel env rm VITE_API_BASE_URL preview "$HEAD_REF" --yes --token "$VERCEL_TOKEN"`. Mirrors how `provision` adds the var. Run `vercel env rm --help` first to confirm the git-branch positional is supported for `rm`; Context7 docs only show `vercel env rm <name> preview --yes`, not the branch argument.
- Fallback if the CLI can't target a branch or can't distinguish "not found" from other errors: use the REST API with curl, matching the existing deployment-delete step. `GET https://api.vercel.com/v9/projects/$VERCEL_PROJECT_ID/env?teamId=$VERCEL_ORG_ID`, filter with `jq` on `key == "VITE_API_BASE_URL"` and `gitBranch == $HEAD_REF`, then `DELETE /v9/projects/$VERCEL_PROJECT_ID/env/{id}?teamId=...` for each match. Verify the endpoint shapes against the Vercel API docs before relying on them.
- Keep `HEAD_REF` in an `env:` block and reference it as a shell variable. Never inline `${{ github.event.pull_request.head.ref }}` into the script (the ref is attacker-controlled).
- Keep `permissions: {}` on the job and the existing fork/Dependabot `if:` guard.
- Update the comment block above the cleanup steps, and the header comment at the top of the workflow, so they say this workflow also owns the Vercel env var, not only the Neon branch.
