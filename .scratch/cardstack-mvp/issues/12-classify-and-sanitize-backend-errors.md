# 12: Backend returns raw internal errors to the frontend, leaking sensitive data (e.g. DB credentials)

> *This was generated by AI during triage.*

**Category:** bug
**Status:** done

**Blocked by:** none. See ADR-0013 for the architecture this brief builds on.

## Agent Brief

**Category:** bug
**Summary:** Any error not explicitly classified is currently serialized verbatim into the client-facing response, which can leak sensitive internal detail (confirmed: a DB auth failure exposes DB credentials). Errors must be classified into known "app errors" (safe to describe) vs "unknown errors" (redacted), enforced by default everywhere, not per-handler.

**Current behavior:**
Handlers commonly return errors straight from the service/repository layer with no mapping (e.g. `CatalogHandler.listSeries` returns `h.catalogSvc.ListSeries(ctx)` unmodified). For any returned error that isn't already a `huma.StatusError`, Huma's default error construction puts that error's raw `.Error()` string into the JSON response body's error detail — with no redaction step. Since lower layers (e.g. the DB connection code) wrap errors with plain `fmt.Errorf("...: %w", err)`, internal detail (in the confirmed case, DB credentials — the DSN is built with `url.UserPassword`, which Go's `net/url` does not mask in `.String()`) can end up serialized straight to the client. A few handlers (`auth_handler.go`) already hand-map some known service errors to specific `huma.ErrorXXX(...)` calls via an inline `switch`, but this is ad hoc, incomplete, and not the default path — anything not explicitly switched on still falls through raw.

**Desired behavior:**
1. Errors are classified using `github.com/itsLeonB/ungerr`'s taxonomy (`AppError` and its concrete kinds — `BadRequestError`, `ConflictError`, `ForbiddenError`, `NotFoundError`, `UnauthorizedError`, `ValidationError`, `TimeoutError`, `TooManyRequestsError`, `UnprocessableEntityError`, `MethodNotAllowedError` — plus `UnknownError`/`InternalServerError` for anything else).
2. A recognized `AppError` returned by a handler produces a response using that error's own HTTP status and safe detail (its `Details()`/message), same behavioral contract `ungerr.AppError` already defines.
3. Any error that is *not* a recognized `AppError` — regardless of where in the call chain it originated — must default to a generic, detail-free response (a fixed "internal server error"-style message, no underlying error text, no stack/connection/query info) at 500. This must be the default for the whole API surface, not something each handler has to opt into individually: a handler/service that forgets to classify an error must not be able to leak it. Enforce this at a single seam (Huma's own error-construction hook — `huma.NewError`/`NewErrorWithContext` — not a gin middleware; this backend runs Huma via `humagin.New`, and Huma finalizes its own JSON response inside `Register()` before gin's outer middleware chain would ever see the error, so a `ctx.Errors`-based gin middleware never fires for Huma-registered operations).
4. Every existing ad hoc per-handler error-to-status mapping (e.g. `auth_handler.go`'s manual `switch` converting service errors to `huma.ErrorXXX(...)`) is migrated onto the same `ungerr` taxonomy, so there is exactly one classification path used consistently across the API, not two competing ones.
5. Whenever an error is treated as "unknown" (redacted to the client), the original, full, unredacted error must still be logged server-side (via the existing logger already used in this codebase), so debuggability isn't lost. Correlating that log entry with the existing otel trace/span id is a nice-to-have, not required.
6. Panics must not bypass this: a recovered panic should also produce the same redacted, generic response shape, not its own separate leak path.

**Key interfaces:**
- Wherever a handler or service currently returns a plain `error` from a failure path that isn't already an intentional, safe `huma.ErrorXXX(...)` call, it should instead return (or the error should be classifiable as) an `ungerr.AppError` for known cases, or be left as an unclassified error that the global default seam treats as unknown/redacted.
- The global default response construction for any non-`ungerr.AppError`, non-`huma.StatusError` error must not include that error's `.Error()` text anywhere in the client-facing JSON body.
- `auth_handler.go`'s existing manual error-to-status `switch` should be replaced by returning `ungerr.AppError` values from the service layer (or an equivalent classification step), so it goes through the same single path as everything else.

**Acceptance criteria:**
- [ ] A handler/service error that is a recognized `ungerr.AppError` produces a response at that error's own status code, with only its intended safe message/details in the body.
- [ ] Any error not recognized as an `ungerr.AppError` (including a raw DB/driver/network error, e.g. reproducing the original DB-auth-failure case) produces a generic, detail-free response — no error message text, no connection info, no credentials — regardless of which handler or layer it originated from.
- [ ] The above holds for every route by default (tested via at least two different, previously-unmapped failure paths in two different handlers/services), not just the one originally reported — i.e. classification is enforced globally, not per-handler.
- [ ] A recovered panic also produces the same generic, detail-free response shape rather than leaking the panic value/stack to the client.
- [ ] When an error is redacted to the client, the full original error is present in the server-side logs.
- [ ] `auth_handler.go`'s manual error-to-status `switch` is removed/migrated so its cases route through the same `ungerr`-based classification as the rest of the API, with existing behavior (status codes returned for each known case) preserved.
- [ ] `go build/vet/gofmt/test ./...` clean, matching this backend's existing verification bar.
- [ ] Reproducing the original repro (wrong DB password, hit `/catalog/series` or any catalog endpoint) now returns a generic error with no DB credentials or connection detail anywhere in the response.

**Out of scope:**
- Changing Huma's own request-validation error responses (query/body decoding failures) — those are already handled by Huma before a handler ever runs and are not part of this leak.
- Building new domain-specific `AppError` subtypes beyond what `ungerr` already provides, unless a specific existing failure case genuinely needs one.
- Frontend changes — this is purely about what the backend sends.
- Any change to log format/aggregation beyond ensuring the unredacted error is logged.

## Comments

Triage session, 2026-09-28 — reported by the maintainer with a live repro (wrong DB password → `/catalog` → Network tab shows DB credentials in the response payload) and a suggested reference pattern (`ginkgo/pkg/middleware/error.go`'s `AppError`/`UnknownError` split from a sibling project).

Verified against the actual code (no live DB needed to confirm the mechanism):
- No error-classification layer exists anywhere in `backend` (`ungerr`/`AppError`/error-middleware patterns absent from both the code and `go.mod`).
- `CatalogHandler.listSeries` and others return service-layer errors unmodified.
- The DB DSN embeds the password in cleartext (`url.UserPassword` + `net/url`'s `.String()` doesn't mask it); the connection-open/ping errors wrap it with plain `fmt.Errorf(...: %w, err)`.
- Confirmed in `huma@v2.39.1/error.go`: `huma.NewError`'s default path puts `err.Error()` straight into the JSON `errors[]` array for any error that isn't a `huma.StatusError` — the exact mechanism that ships the leak to the client.
- `auth_handler.go` already hand-maps some errors via an inline `switch` to `huma.ErrorXXX(...)`, but inconsistently — confirming this needs a single default path, not scattered per-handler fixes.

Grilling round (maintainer-confirmed):
- Adopt `github.com/itsLeonB/ungerr` as a new dependency rather than reimplementing the taxonomy locally — it's already framework-agnostic (no gin/huma coupling) and this backend already depends on sibling `itsLeonB` org repos (`ezutil`, `go-authkit`, `go-crud`) the same way; `ungerr` is tagged (`v0.5.0` latest stable) so it resolves like any other dependency.
- **Fact found, not a decision**: `ginkgo`'s gin-based error middleware does not transplant onto this backend as-is — Huma (`humagin.New`) finalizes its own JSON response inside `Register()` before gin's outer middleware chain runs, so a `ctx.Errors`-reading gin middleware never sees the error. The equivalent seam here is Huma's own `NewError`/`NewErrorWithContext` override.
- Fix must be a single global seam (redact-by-default), not a targeted patch on the DB path — any unclassified error anywhere is the real bug.
- Existing scattered mappings (`auth_handler.go`'s switch) get migrated onto the same taxonomy — one consistent path, not two.
- Raw errors are always logged server-side in full even when the client response is redacted; trace-id correlation is a nice-to-have.

Recorded as ADR-0013 (`docs/adr/0013-error-classification-via-ungerr-at-a-huma-level-seam.md`). No `CONTEXT.md` entry — this is infrastructure/technical, not business-domain vocabulary.
