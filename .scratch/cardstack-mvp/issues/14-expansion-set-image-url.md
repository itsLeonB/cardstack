# 14: `expansion_sets` have no stored cover image

## Agent Brief

**Category:** enhancement
**Summary:** Persist and display each Expansion Set's cover image, sourced from the same pokemonasia listing page ingestion already scrapes for Series/Code/Name/ReleaseDate.

**Current behavior:**
`ExpansionSet` has no image field. The ingester's expansion-listing parser reads Series, Code, Name, and ReleaseDate out of each listing entry, but discards the cover-image element that's also present in that same markup. `ExpansionSetSummary` (the DTO backing `GET /catalog/series`) has no image field either. The catalog browse page renders one tile per Expansion Set with name, code, and release date only — no image, no layout slot reserved for one.

**Desired behavior:**
1. The expansion-listing parser also captures the listing's cover-image URL (verified live: each listing's image sits in a dedicated image container inside the same clickable block the parser already reads Series/Code/Name/ReleaseDate from). Capture the source's URL exactly as given — filenames are not a fixed, constructible pattern across sets (confirmed two real examples differ in casing/format), unlike per-card images, which this ingester already builds from a fixed template. A listing with no image element yields an empty string, not an error and not a skipped listing.
2. `ExpansionSet` persists this as a new non-nullable string field, empty-string default when absent — same convention `Card.ImageURL` already uses, not a nullable column.
3. The Expansion Set upsert path (insert and update) writes this field like every other listing-derived field, so a full ingestion run backfills existing rows as a side effect.
4. Backfilling existing rows must not require a full re-ingestion (re-crawling every card of every set is slow and unnecessary just to pick up an image URL). Add a lightweight, opt-in path that enumerates every target Expansion Set listing exactly as full ingestion already does (same discovery/pagination, same Series/Expansion-Set upsert calls) but stops there — it must not enumerate, fetch, or upsert anything at the Card or Rarity level for any set. This should reuse the existing listing-enumeration and Series/Expansion-Set upsert logic rather than duplicating it; it's a subset of the existing ingestion run, not a separate scraper.
5. `ExpansionSetSummary` exposes the field (camelCase `imageUrl`, matching the existing `Card` image field's JSON naming).
6. The catalog browse page's per-Expansion-Set tile displays this image when present, degrading gracefully (no broken-image icon, no layout shift) when it's empty.

**Key interfaces:**
- `ExpansionSet` entity: new `ImageURL string` field, `not null default ''`, mirroring `Card.ImageURL`'s existing convention.
- The expansion-listing parser's per-listing result type: gains an image-URL field alongside its existing Series/Code/Name/ReleaseDate fields.
- The Expansion Set upsert function: writes ImageURL on both the insert and update branches.
- A new opt-in ingestion entry point (a flag/mode alongside the existing debug-oriented ones) that runs listing enumeration plus the Series/Expansion-Set upsert step only, and returns/logs a summary of how many Expansion Sets were touched — without invoking the per-set card-crawl step at all.
- `ExpansionSetSummary` DTO and its mapper: new `imageUrl` JSON field, populated from the entity.
- Catalog browse page's per-Expansion-Set tile component: renders the image when non-empty.

**Acceptance criteria:**
- [x] A full ingestion run populates `expansion_sets.image_url` for every Expansion Set whose listing has an image (as a side effect of its existing upsert step).
- [x] The new lightweight image-sync path also populates `expansion_sets.image_url` for every existing Expansion Set row whose listing has an image, without fetching or writing anything under Card or Rarity for any set — verify by timing/observing that it completes without the per-set card-crawl work full ingestion does (e.g. no card-detail or rarity-sweep requests fired).
- [x] Running the lightweight path against a set that isn't in the DB yet behaves consistently with the existing upsert convention (create-or-update), not a hard failure.
- [x] A listing with no image element ingests successfully with `image_url = ""`, via either path.
- [x] `GET /catalog/series`'s `series[].expansionSets[]` and `ungroupedExpansionSets[]` entries include a populated `imageUrl`.
- [x] The catalog browse page shows each Expansion Set's cover image in its tile when present; a set with none renders its current text-only tile, no broken-image icon.
- [x] `go build/vet/gofmt/test ./...` clean; frontend lint/typecheck/test clean.

**Out of scope:**
- Series image (tracked separately as its own ticket — Series has no image source on this same page; see #15).
- Constructing/normalizing the image URL to a fixed filename template — store the source's own URL verbatim.
- Any change to Card image handling — already implemented, unaffected.
- Expansion Set detail page redesign beyond adding the image if the agent chooses to place it there too.
- Changing full ingestion's existing behavior — it still upserts everything it always has; the lightweight path is additive, not a replacement.

## Comments

Triage session, 2026-09-28 — reported by the maintainer via `/triage`, bundled with a related but separately-scoped Series-image request (split into #15 since Series has no known image source and needs its own investigation).

Verified before writing this brief:
- `ExpansionSet` entity (`internal/domain/entity/expansion_set.go`) and `Series` entity have no image field; only `Card` does (`Card.ImageURL string`, `not null default ''`).
- Neither `ExpansionSetSummary` nor `SeriesSummary` DTOs expose an image field.
- Live-fetched `https://asia.pokemon-card.com/id/card-search/`: each `li.expansion` entry's `a.expansionLink` contains a `div.leftColumn > div.imageContainer > img[src]` alongside the already-scraped `div.rightColumn` (Series/Name/ReleaseDate). Two real examples confirm the filename isn't a fixed pattern (`.../products/idn_ma6_pkg.png` vs `.../products/MATL_PKG_IDN.png`) — must be scraped verbatim, can't be constructed the way `cardImageURL` constructs per-card images from a numeric id.
- The existing per-listing parser (`parseExpansionListings`) and the existing `upsertExpansionSet` (which already fully overwrites Name/LocaleID/SeriesID/ReleaseDate on every run) are the natural extension points — no ingestion architecture change needed.
- No `.out-of-scope/` entry or ADR covers this; not already implemented.

No ADR: this is a straightforward schema/scrape addition matching an existing convention (`Card.ImageURL`), not an architectural decision.

Follow-up, 2026-09-28 — maintainer asked for a lightweight backfill path instead of relying on a full re-ingestion to pick up images on existing rows: a full run re-crawls every card of every set, which is slow and wasteful just to backfill one field. Added acceptance criteria and a key interface for an opt-in mode that only enumerates listings and upserts Series/Expansion-Set rows (the cheap, already-existing discovery step), skipping the per-set card-crawl step (`ingestSet` in the current code, and everything it calls) entirely. This mirrors the existing precedent of `CleanupStaleRarities` being a separate opt-in operation alongside the main ingestion run, rather than a new standalone scraper.
