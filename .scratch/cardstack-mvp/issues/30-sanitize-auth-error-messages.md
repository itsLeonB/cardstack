# 30: Auth errors leak authkit internals to the client

**Category:** bug
**Status:** ready-for-agent

**Blocked by:** None (can start immediately)

## Agent Brief

**Category:** bug
**Summary:** Auth endpoints return authkit's raw sentinel text (e.g. `"authkit: invalid credentials"`) as the response `detail`, and the login form shows it to users. Responses must carry generic, authkit-free messages.

**Current behavior:**
- `mapAuthError` in `backend/internal/adapters/http/handler/auth_handler.go` passes `err.Error()` into every `ungerr` error it builds. The Huma error classifier (`backend/internal/adapters/http/huma/errors.go`) then sends that string as `detail`.
- Logging in with a wrong password or a nonexistent email returns `{"title":"Unauthorized","status":401,"detail":"authkit: invalid credentials"}`. Both cases already map to `ErrInvalidCredentials`, and `frontend/src/routes/login.tsx` displays `response.data.detail` verbatim.
- Every other branch leaks the same way: `ErrUserExists`, `ErrSessionNotFound`, `ErrTokenInvalid`, `ErrTokenExpired`, `ErrTokenNotFound`, `ErrUserNotFound`, `ErrNotVerified`, `ErrTooManyRequests`.

**Desired behavior:**
- Each branch of `mapAuthError` returns a fixed, human-readable message that contains no "authkit" text and no sentinel wording.
- Wrong password and unknown email return the identical 401 message (no account enumeration). Suggested: "Invalid email or password."
- Session and token errors (`ErrSessionNotFound`, `ErrTokenInvalid`, `ErrTokenExpired`, `ErrTokenNotFound`) share one generic 401 message. Suggested: "Session expired or invalid. Please log in again."
- Other branches get similarly generic messages (conflict, forbidden, rate limit, not found). Status codes are unchanged.
- The unclassified default branch is unchanged: the error still passes through untouched to the global redaction seam.

**Key interfaces:**
- `mapAuthError` only. Frontend needs no change: `login.tsx` and `register.tsx` already render `detail`, and the login fallback "Invalid email or password." matches the new message.

**Acceptance criteria:**
- [ ] Login with a wrong password and with an unknown email both return 401 with the same generic `detail`, containing no "authkit"
- [ ] Every sentinel in `mapAuthError` maps to a message with no "authkit" text, with unchanged HTTP status
- [ ] `TestAuthHandler_Login_InvalidCredentials` (currently asserts `authkit.ErrInvalidCredentials.Error()` as the detail) asserts the new generic message instead
- [ ] `TestMapAuthError_KnownStatuses` also asserts the message does not contain "authkit"
- [ ] `TestMapAuthError_UnknownIsLeftForTheGlobalSeam` still passes
- [ ] Backend build, vet and tests pass

**Out of scope:**
- Frontend changes
- The Huma error classifier and non-auth handlers
- Logging the original authkit error server-side (optional; add only if trivial)
