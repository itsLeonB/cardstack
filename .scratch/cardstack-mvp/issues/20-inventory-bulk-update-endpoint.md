# 20: Inventory bulk update endpoint

**Category:** enhancement
**Status:** ready-for-agent

**Blocked by:** None (can start immediately)

## Agent Brief

**Category:** enhancement
**Summary:** Add one backend endpoint that applies many Inventory Entry quantity changes to a Collection in a single request, so a debounced UI can send +/- and typed changes as a batch. This ticket is backend only.

**Current behavior:**
Inventory Entries change one at a time: add (409 if the Card is already in the Collection), update quantity, and remove are separate endpoints. Quantity must be at least 1 and removing is only possible through the delete endpoint.

**Desired behavior:**
A new endpoint on a Collection takes an ordered list of `{cardId, quantity}` items, where `quantity` is the absolute target quantity (not a delta, so a retried request is idempotent), and applies them in order inside one transaction with the Collection row locked, using the capacity rule that already exists.

Per item, in submitted order:
- `quantity` 0 removes the Inventory Entry (a no-op if it does not exist).
- `quantity` above 0 creates the entry if it is absent, or sets its quantity if present (upsert; it does not 409).
- If applying the item would push the Collection's summed quantity past its capacity limit (when a limit is set), that item is **declined** and not applied. Items that decrease or keep the quantity are never declined for capacity, even when the Collection is already over its limit.
- An unknown `cardId` declines that item.
- Declined items do not stop the rest: the rest of the batch is applied (partial success). Because items are processed in order, when capacity runs short the later items are the ones declined, which is how the UI ends up declining the last card the user pressed.

The response is 200 with one result per submitted item, in order: `cardId`, the resulting `quantity` (0 when removed or absent), `status` (`applied`, `removed` or `declined`) and, for declined items, a machine-readable `reason` (`capacity_exceeded` or `card_not_found`) plus a human-readable message. The client must be able to reconcile every row from this response alone.

Request validation: another profile's or a missing Collection is 404 (same as every other Collection operation), duplicate `cardId`s in one request are rejected with 400, a negative quantity is rejected, and an empty list or a list above a documented maximum size is rejected. Authentication and the global CSRF guard apply as for the other mutating routes.

**Key interfaces:**
- A new route on the Collection's entries resource (for example `PATCH /collections/{id}/entries`) with request DTO carrying `ProfileID`, `CollectionID` and the items, so the service signature is `(ctx, dto)` per the backend conventions.
- A per-item result DTO and status/reason enums in the OpenAPI schema.
- Reuse the existing owner-scoped Collection lookup with row lock, `crud.Transactor.WithinTransaction`, and plain `crud.Repository` calls (check-then-act), as documented in the backend conventions. Do not rely on `RowsAffected`.
- Regenerate `openapi.json`.

**Acceptance criteria:**
- [ ] A batch mixing add, increase, decrease and remove is applied and each result reports the resulting quantity and status
- [ ] Quantity 0 removes an existing entry, and is a no-op result for an absent one
- [ ] An item that would exceed capacity is declined with `capacity_exceeded`, earlier items in the batch stay applied, and later items still get evaluated against the remaining capacity
- [ ] A decrease on a Collection already over its limit is applied
- [ ] Unknown `cardId` is declined with `card_not_found` while the rest is applied
- [ ] Duplicate `cardId`s, negative quantities, empty and oversized batches are rejected with the documented client errors
- [ ] Foreign or missing Collection returns 404 and changes nothing
- [ ] Missing CSRF header returns 403, unauthenticated returns 401
- [ ] Unit tests against mocked repositories cover the capacity and status logic, and a real-Postgres route test covers the flow end to end and concurrent batches on one Collection serialize
- [ ] `go build ./...`, `go vet ./...`, `gofmt -l .` and `go test ./...` pass and `openapi.json` is regenerated

**Out of scope:**
- Any frontend change (ticket 22 consumes this)
- Removing or changing the existing single-entry endpoints
- Cross-Collection or Master Inventory operations
