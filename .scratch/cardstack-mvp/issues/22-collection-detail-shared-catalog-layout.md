# 22: Collection detail page on the shared catalog layout, with filters and stepper editing

**Category:** enhancement
**Status:** ready-for-agent

**Blocked by:** 20 (Inventory bulk update endpoint), 21 (Catalog faceted multi-value filters)

## Agent Brief

**Category:** enhancement
**Summary:** The Collection detail page lists its cards with the same layout and components as the catalog, supports the same filters scoped to that Collection, and edits quantities with +/- buttons or typing, saved automatically in debounced batches.

**Current behavior:**
- The Collection detail page shows its Inventory Entries in its own compact list, each row with a quantity input and Save and Remove buttons, and a separate name-search picker to add a Card.
- The endpoint listing a Collection's entries returns every entry with no filtering or pagination.
- The catalog page has its own results grid and filter panel, not shared with the Collection page.

**Desired behavior:**
- The catalog's card tile, results grid, filter panel and pagination are shared components used by both the catalog search and the Collection detail page. There is one implementation of each, not a copy.
- The Collection's entries endpoint accepts the same filter parameters as catalog search (name, card number, and multi-value Expansion Set, Rarity, Category, Tag) plus pagination, and returns card summary and quantity with pagination metadata. A facets endpoint scoped to the Collection returns filter options computed only from the cards in that Collection, using the same faceted rule as ticket 21. Ownership rules are unchanged: another profile's Collection is 404.
- The Collection page shows each card as a catalog tile with a quantity control: a minus button, a number input and a plus button. The user can click or type; there is no save button.
- Changes are applied optimistically and sent with a debounce (roughly half a second of quiet, a named constant), batching every changed card into one call to the bulk endpoint from ticket 20. Items in the batch are ordered by when the user last changed them, oldest first, so that if capacity runs short the most recently pressed card is the one declined.
- A declined item (capacity) reverts that tile to the server's returned quantity and shows an error message tied to that card; the other items in the batch keep their changes. A network failure reverts the affected tiles and shows an error.
- Reducing a quantity to 0 removes the entry on the server, but the tile stays on screen showing 0 until the user reloads or navigates away and comes back; on return the card is gone. A card at 0 can be increased again in place. The cached list must not be reused stale on return (it refetches on mount), or the removed card would still show.
- Filters and page live in the URL search params like the catalog. Changing filters or page while edits are pending must not lose them (flush the pending batch first).
- The old compact list, Save and Remove buttons and single-entry calls are removed from this page. The name-search "add a Card" picker stays until ticket 23 replaces it.

**Key interfaces:**
- Shared UI components extracted from the catalog search page (card tile, results grid, filter panel, pagination) with a slot for a per-card control, so the catalog can render either no control or a quantity control (ticket 23).
- The Collection entries list endpoint's query parameters and response (items plus pagination meta), and a Collection-scoped facets endpoint, with the filter and facet logic from ticket 21 reused on a base set restricted to the Collection's cards.
- A debounced batch-update hook on top of the generated bulk endpoint client.

**Acceptance criteria:**
- [ ] Catalog search and the Collection detail page render tiles, grid, filters and pagination from the same shared components
- [ ] Filtering a Collection by any catalog filter returns only that Collection's cards, and filter options reflect only cards in that Collection
- [ ] Backend tests (mocked repository units plus real-Postgres routes) cover filtering, pagination, facets scoping and 404 for a foreign Collection
- [ ] Clicking + or - and typing a number both change the quantity with no save button
- [ ] Several quick changes to several cards produce a single bulk request after the debounce, ordered oldest change first (test with fake timers)
- [ ] A capacity-declined item reverts to its server quantity with an error message while the other items in the batch stay applied
- [ ] Going to 0 keeps the tile visible at 0 until reload or leaving and returning, after which the card is gone
- [ ] Changing a filter or page with pending edits flushes them first
- [ ] Old row-based list, Save and Remove UI are gone from this page, with tests updated accordingly
- [ ] Both verification scripts pass, `openapi.json` and the generated client are regenerated

**Out of scope:**
- Adding cards from the catalog page (ticket 23)
- Guest-related limits (ticket 24)
- Infinite scroll or virtualization (ticket 25)
- Removing the old single-entry backend endpoints
