## Agent Brief

**Category:** bug
**Summary:** The ingester scrapes the wrong field into Card Rarity (it's actually each card's Regulation Mark), and its card-enumeration strategy silently undercounts some Expansion Sets.

**Current behavior:**
For each card, the ingester scrapes a single-letter/short code from the card detail page and stores it as the card's rarity (`rarities.code` / `cards.rarity_id`). That field is actually the card's **Regulation Mark** (a letter, `A`-`J`, governing tournament format legality — see `CONTEXT.md`'s Regulation Mark entry) — it is unrelated to print rarity. The real print rarity ("Kelangkaan" in the source site's Indonesian UI: `C`/`U`/`R`/`RR`/`RRR`/`PR`/`TR`/`SR`/`HR`/`UR`/"Tanpa Tanda"/`K`/`A`/`AR`/`SAR`/`S`/`SSR`/`ACE`/`BWR`/`MUR`/`MA`/`FUR`) does not appear anywhere on the card detail page at all.

Separately, card enumeration for a set currently issues three passes filtered by a `regulation` parameter (partitioning by format-legality bucket) and dedupes overlapping results across them. This has been confirmed to *undercount* some sets: for at least one real set, the union of all three partitioned passes reached only 178 of the set's true 199 cards. The three-way partition's third bucket ("Lainnya"/Others) returns zero cards site-wide and does not correspond to any real, official Pokémon TCG format.

**Desired behavior:**

1. **Enumeration**: discovering a set's card ids uses a single pass with the `regulation` query parameter set to its "all" value (not omitted, not partitioned into three separate values) — confirmed to reliably return the complete, true card count for a set. The existing three-way partition and its cross-bucket dedup logic are removed.
2. **Rarity**: each card's rarity code is determined from the results-list endpoint's rarity filter, not the detail page. That filter accepts a numeric id per rarity code (e.g. one id means `C`, another means `SAR`, etc. — undocumented and must not be assumed stable across a code change); querying the results-list endpoint with one filter id at a time and paginating returns exactly the card ids carrying that rarity. The full set of (id → code) pairs for a request is discoverable from that same results-list page's own filter-option markup (each option exposes both its query value and its display label) — parse this dynamically per request rather than hardcoding the mapping, so an id-to-code correction or a newly-introduced code doesn't require a code change. A card not found under any known rarity id should not block ingestion of the rest of the set (log and continue, consistent with how other per-item ingestion failures are already handled elsewhere in this ingester).
3. **Regulation Mark**: the field currently mis-scraped into rarity (the detail page's single-letter code) is instead captured as the card's Regulation Mark, stored in the card's Game-specific attributes bag under its own key, distinct from whatever key any prior format-legality label used. No Standard/Expanded/other format-legality label is computed or stored — that determination depends on which marks are *currently* tournament-legal, a fact that changes over time and shouldn't be frozen into ingested data (see ADR-0010).
4. **Idempotency**: a full re-run of the ingester against the same Expansion Set continues to update existing Card rows in place (matching the existing upsert behavior) rather than creating duplicates, and corrects any Card's rarity reference left wrong by the current bug.
5. **Cleanup of prior bad data**: the CLI gains a new, explicit, **opt-in, off-by-default** flag that performs a one-time deletion of `rarities` rows that were populated with Regulation Mark letters (by the current bug) rather than real rarity codes, scoped to rows no longer referenced by any Card. It must refuse to delete (and report, not silently skip) any such row still referenced by a Card, since that would indicate the corrected re-ingestion hasn't fully run yet. Running the CLI without this flag must not perform any deletion.

**Key interfaces:**
- Whatever type currently represents one parsed card-detail page (holding fields like name, category, tag, rarity code, local id, illustrator, and a caller-filled format-legality label) should stop populating a rarity field from the detail page and instead expose the detail page's own regulation-mark letter as its own field.
- Whatever function currently issues the three regulation-partitioned enumeration passes for a set (and dedupes across them) should issue one pass with the "all" regulation value instead, and no longer need dedup logic for that purpose.
- A new step, run once per enumerated card (or batched per set, whichever fits the existing per-set flow better), resolves that card's rarity code via the results-list endpoint's rarity filter as described above, and that resolved code is what's find-or-created into the `rarities` lookup table (per ADR-0009 — still scoped `(game, code)`, still find-or-create, no seeding).
- The card entity's Game-specific attributes bag gains the Regulation Mark value under a clearly-named key; whatever key a prior format-legality label used should no longer be populated.
- The CLI entrypoint gains a new flag (naming and exact shape is the agent's call — keep it consistent with the existing debug-oriented `-series` flag's style) that triggers the stale-`rarities`-row cleanup described above instead of normal ingestion.

**Acceptance criteria:**
- [x] A set's card-id enumeration uses a single request with `regulation` set to its "all" value, not a 3-way partition, and this is covered by a test asserting no per-partition dedup logic runs.
- [x] A card's rarity code is resolved via the results-list rarity filter (a fixture-based test simulating that filter's response format, with dynamically-parsed id→code labels), not via any detail-page field.
- [x] A results-list page's rarity filter options are parsed from that page's own markup (id/label pairs), not from a hardcoded map — a test using a fixture with an unfamiliar/synthetic rarity id+label must still resolve correctly.
- [x] The card detail page's regulation-mark letter is captured into the card's attributes under its own key, verified via a mapper-level test with a realistic fixture.
- [x] No format-legality label (Standard/Expanded/other, however it was previously keyed) is produced by ingestion.
- [x] Re-running the ingester against an already-ingested Expansion Set updates existing Card rows' rarity reference to the corrected value rather than creating duplicate Card or Rarity rows (idempotency test).
- [x] A card whose rarity can't be resolved from any known filter value logs a failure and does not abort ingestion of the rest of its set.
- [x] The CLI's default invocation (no new flag) performs no `rarities` deletion.
- [x] The CLI's new opt-in flag deletes only `rarities` rows matching the old Regulation Mark letters that have zero referencing Cards, and reports (without deleting) any matching row that still has referencing Cards.
- [x] `go build/vet/gofmt/test ./...` clean, matching this ingester's existing verification bar.
- [x] A real (or close-to-real, fixture-driven) run demonstrates: (a) a set previously known to undercount now ingests its true full card count, and (b) at least one card's rarity now resolves to a real Kelangkaan code rather than a Regulation Mark letter.

**Out of scope:**
- Modeling "Lainnya"/a third format bucket as real — confirmed non-functional and not an official format (see the linked research doc).
- Computing or storing Standard/Expanded format legality anywhere — explicitly deferred to a future consumer, since the legal-mark floor changes with each yearly rotation.
- Any change to Card Category, Card Tag, or other extraction logic already working correctly.
- English- or Japan-region card data — this ticket only concerns the already-in-scope Indonesian-locale Series.
- Building a general "retry a specific failed card/set" CLI mode beyond what already exists — only the new one-time cleanup flag described above is in scope for CLI changes.

## Comments

Triage session, 2026-09-27 — reported by the maintainer: rarity data in the database (`A`-`J`-style single-letter codes) didn't match the site's own rarity ("Kelangkaan") filter values, which are visible on the results-list page but absent from the card detail page. Verified live against `asia.pokemon-card.com`:

- The detail page's `span.alpha` field is the card's Regulation Mark (confirmed via the site's own `/id/rules/regulation/` page and cross-referenced against Bulbapedia and `pokemon.com`'s official 2026 rotation announcement — see the research doc).
- The results-list page's `rarity[]=N` filter (~22 values) correctly and exhaustively partitions a set's cards by real rarity code — confirmed by comparing the deduplicated union of every rarity-filtered pass against the set's true total.
- The existing `regulation=1/2/3` enumeration strategy undercounts: the same set's true total (199, matching the rarity-filter union) exceeded what the 3-way partition reached (178). Explicitly setting `regulation=all` reliably returns the true total instead.
- Primary-source research (`.scratch/cardstack-mvp/research/pokemon-tcg-regulation-marks.md`) confirmed: Standard/Expanded legality is a moving floor over Regulation Mark letters (not a fixed bucket), no official third format exists, and the site's own "Lainnya" filter value returns zero cards.

Decisions made during grilling (maintainer-confirmed): drop the regulation-partitioned enumeration for a single `regulation=all` pass; source rarity from the results-list filter with dynamically-parsed id→code mapping (not hardcoded); replace the derived format-legality attribute with the real per-card Regulation Mark; gate the stale-data cleanup behind a new opt-in CLI flag; one ticket covering both the rarity fix and the enumeration-completeness fix, since both require the same full re-scrape. Recorded as ADR-0010 and a new `CONTEXT.md` Regulation Mark entry.

Implementation, 2026-09-27 — `backend-agent` in worktree `fix/pokemon-asia-rarity-ingestion`, commit `210d45b` (`fix(backend): source Card Rarity from the results-list filter, not Regulation Mark`), merged into `claude/funny-hypatia-mmz226`. Independently re-verified live against `asia.pokemon-card.com` during implementation: `regulation=all` matches the rarity-bucket union exactly on two more sets (`MA1`: 184 both ways, `AS1a`: 150 both ways), and the rarity[] filter widget is present on every results-list response regardless of query, so no extra fetch is needed to harvest the id→code map.
