# 21: Catalog filters: multi-value checkboxes with dependent (faceted) options

**Category:** enhancement
**Status:** done — implemented (backend `f906977` + `1166d16`, frontend `8871fc2` + `a03b5a2`), merged to `main`.

**Blocked by:** None (can start immediately)

## Agent Brief

**Category:** enhancement
**Summary:** Catalog search accepts several values per filter (checkboxes), and the options each filter offers are limited to values that exist among the cards matching the other active filters.

**Current behavior:**
- The card search filter takes at most one value each for Expansion Set, Rarity, Category and Tag, plus a name and a card number text filter.
- The Series, Rarity, Category and Tag option lists are static: they list every value in the catalog no matter what else is selected, so choosing an Expansion Set still offers Rarities that set has no cards for.

**Desired behavior:**
- Expansion Set, Rarity, Category and Tag each accept multiple values. Within one filter the values combine with OR (a card matches if it has any selected value; for Tag, if it carries any selected Tag), and across filters they combine with AND. Card name and card number stay single text inputs.
- Filter options are **faceted**: for each filter, the available options are the values present on cards that match every *other* active filter, with that filter's own selection excluded from the calculation. So selecting one Expansion Set still lets the user add a second one, while the Rarity options shrink to that set's Rarities. Example: with the Expansion Set "Deck Taktik" selected the Rarity options do not include FUR, SAR or SR, while with "30th CELEBRATIONS" selected they do.
- A value that is currently selected stays visible and checked even if the other filters have made it unavailable, so the user can always uncheck it.
- The UI shows each of these filters as a checkbox group (Expansion Sets grouped under their Series, including the ungrouped ones), next to the two text inputs. Checking or unchecking updates the results and the other groups' options. The selected values live in the URL search params so a filtered view is linkable, and the URL round-trips multiple values.
- The facet calculation and filter conditions are designed so they can later be applied on top of a narrower base set (ticket 22 scopes them to one Collection's cards) without a rewrite.

**Key interfaces:**
- `CardFilter`: the single-valued facet fields become collections of values (Expansion Set ids, Rarity ids, Categories, Tags); `Name` and `LocalID` stay single.
- The catalog search endpoint's query parameters accept repeated values for those filters, and the OpenAPI schema and generated frontend client reflect it.
- A new facets endpoint (for example `GET /catalog/facets`) takes the same filter parameters and returns the available options per facet using the rule above. It replaces the need for the static Rarity, Category and Tag list calls on the search page; keep the existing endpoints if other pages use them.
- The catalog search page's filter components and search-param schema.

**Acceptance criteria:**
- [x] Search with several Expansion Sets, Rarities, Categories or Tags returns cards matching any value within a filter and all filters together
- [x] The facets endpoint, given an Expansion Set filter, returns only the Rarities, Categories and Tags present on that set's cards, and returns the Expansion Set options computed without the set filter itself
- [x] A backend test with fixture cards proves the Deck Taktik versus 30th CELEBRATIONS behavior (a Rarity absent from one set's cards is absent from its options and present for the other)
- [x] No filter selection is silently dropped: a selected but now unavailable value is still returned as selected/visible to the client contract or handled in the UI as described
- [x] The search page renders checkbox groups for the four filters plus the two text inputs, and options update when other filters change
- [x] Multiple selected values round-trip through the URL (reload and shared link reproduce the same view)
- [x] Existing single-value filtering behavior and browse-by-set pages keep working
- [x] Service unit tests use mocked repositories, real-Postgres tests cover the queries, frontend tests cover the interaction, and both verification scripts pass with `openapi.json` and the generated client regenerated

**Out of scope:**
- Filtering inside a Collection (ticket 22)
- Facet counts next to each option
- Guest limits on filtering (ticket 24)
- Infinite scroll or pagination changes (ticket 25)
