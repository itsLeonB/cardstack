# 13: /catalog series and Expansion Sets are not ordered by release date

> *This was generated by AI during triage.*

**Category:** enhancement
**Status:** ready-for-agent

**Blocked by:** none.

## Agent Brief

**Category:** enhancement
**Summary:** The catalog browse and search surfaces should order Series, Expansion Sets, and Cards by release date descending (most recent first). Series itself carries no release date today; it must derive one from its Expansion Sets rather than gaining a new stored column.

**Current behavior:**
`CatalogRepository.ListSeries` orders Series alphabetically by name only — release date plays no part in Series ordering, and `Series` has no release-date-like field at all. `CatalogRepository.ListExpansionSets` and `ListUngroupedExpansionSets` (the Expansion Set listings nested under `GET /catalog/series`) order ascending by release date (oldest first), with unknown dates sorting last. `CatalogRepository.SearchCards` (backing `/catalog/search`) also orders its results ascending by its joined Expansion Set's release date, oldest first. The frontend applies no client-side sorting anywhere in the catalog routes — it renders API responses in the order the backend returns them.

**Desired behavior:**
1. Series order descending by release date (most recent first). A Series has no release date of its own; its ordering date is derived as the earliest `release_date` among its own Expansion Sets, computed at query time — not stored on the `Series` entity, not backfilled into a column, not touched by ingestion.
2. Expansion Sets nested within a Series, and standalone "ungrouped" Expansion Sets (no Series), also order descending by release date (most recent first) — flipped from today's ascending order.
3. Card search results (`SearchCards`) also order descending by their Expansion Set's release date — flipped from today's ascending order.
4. Any Series, Expansion Set, or Card whose relevant release date is unknown (NULL, or — for a Series — none of its Expansion Sets have a known date) sorts last, regardless of the descending direction. Postgres defaults `DESC` to `NULLS FIRST`, so this needs an explicit `NULLS LAST`.
5. Every existing tie-breaker (by name, or by id, wherever one is already used to keep multi-row ordering stable) keeps its current ascending direction. Only the release-date axis flips to descending; alphabetical/id tie-breaking is unaffected.
6. `expansion_sets.release_date` gains an index, added proactively (not in response to a measured slow query) since every ordering path above now sorts on it.

**Key interfaces:**
- `CatalogRepository.ListSeries`: must order by each Series's derived earliest Expansion Set `release_date`, descending, unknown-last, tied-broken by name ascending — instead of today's `name ASC` only. This requires joining/aggregating against Expansion Sets rather than querying `Series` alone.
- `CatalogRepository.ListExpansionSets` / `ListUngroupedExpansionSets`: flip from `release_date ASC NULLS LAST` to `release_date DESC NULLS LAST`; existing name tie-breaker stays ascending.
- `CatalogRepository.SearchCards`: flip its Expansion-Set-release-date ordering component from ascending to `DESC NULLS LAST`; all of its other existing tie-breakers stay ascending.
- `Series` entity: no new field. Its release date for ordering purposes is derived, never persisted (see `CONTEXT.md`'s Series entry, updated during triage to record this).
- Database schema: a new index on `expansion_sets.release_date`.

**Acceptance criteria:**
- [ ] `GET /catalog/series` returns Series ordered by the most recent release date among each Series's own Expansion Sets, most-recent-first.
- [ ] A Series whose Expansion Sets all have unknown release dates (or, if reachable, a Series with no Expansion Sets at all) sorts after every Series with a known date.
- [ ] Expansion Sets nested within each Series in that same response are ordered most-recent-first (flipped from today).
- [ ] The `ungroupedExpansionSets` list in that same response is also ordered most-recent-first.
- [ ] `/catalog/search` card results are ordered most-recent-first by their Expansion Set's release date.
- [ ] Wherever a name (or id) tie-breaker already exists in any of the above, it remains ascending — only the release-date axis flipped.
- [ ] A query plan against `expansion_sets.release_date` uses the new index rather than a sequential scan (or equivalent evidence the index is actually being created/used).
- [ ] No frontend changes are required or made — the frontend already renders catalog responses in API order with no client-side sorting.
- [ ] `go build/vet/gofmt/test ./...` clean, matching this backend's existing verification bar.

**Out of scope:**
- Adding a stored/persisted `release_date` (or similar) column on `Series` — this ticket derives it on read only.
- Any change to ingestion — Series never gets a release date written to it by the ingestion path, now or after this ticket.
- Any change to `SearchCards`'s filtering, pagination, or any ordering axis other than release date.
- Any change to how `/catalog/search` or `/catalog` display or format release dates in the UI.

## Comments

Triage session, 2026-09-28 — reported by the maintainer via `/triage` with the core insight already supplied (Series has no release date, but can derive one from its Expansion Sets' earliest release date).

Verified against the actual code before grilling:
- `Series` entity (`internal/domain/entity/series.go`) has no release-date field.
- `CatalogRepository.ListSeries` orders by `name ASC` only — confirmed the reported gap.
- `CatalogRepository.ListExpansionSets` / `ListUngroupedExpansionSets` already order by `release_date ASC NULLS LAST, name ASC` — correct mechanism, wrong direction relative to what this ticket settles on.
- Frontend (`frontend/src/routes/catalog/index.tsx`) does no client-side sorting; confirmed this is backend-only work.
- No prior ADR or `.out-of-scope/` entry covers this; ADR-0008 (`docs/adr/0008-series-groups-expansion-sets-optionally.md`) explicitly anticipated Series eventually carrying "own attributes like release-date range or ordering."

Grilling round (maintainer-confirmed decisions):
- Scope is the whole `/catalog`-family ordering, not just Series: sets-within-series, ungrouped sets, and `SearchCards` all flip to descending too (maintainer explicitly widened scope beyond the original ask during grilling).
- `Series.release_date` is computed at read time (`MIN` over its Expansion Sets), never stored — no migration, no ingestion-path change.
- Unknown dates sort last in all cases, consistent with the existing `NULLS LAST` convention already used elsewhere in this repository.
- All existing tie-breakers stay ascending; only the release-date axis flips.
- An index on `expansion_sets.release_date` is added proactively per the maintainer's standing preference ("good engineering behavior to index a sortable column on a growing table"), not because current data volume demands it.

Domain modeling: added one sentence to `CONTEXT.md`'s Series glossary entry recording that Series's release date is derived (not stored), cross-referencing ADR-0008. No new ADR — this is a query-ordering decision, not a hard-to-reverse architectural one (ADR-0008 already covers the "Series as first-class entity" decision this builds on).
