# Backend sign-in (Clerk)

The API authenticates only by an `Authorization: Bearer` Clerk session token (ADR-0015); it holds no credentials, sessions or cookies. It verifies the signature against the instance's keys (fetched with the secret key and cached), the expiry, the issuer, and that the token's authorized party is one of the frontend origins (`APP_CLIENT_URLS`, or the Admin app's `ADMIN_CLIENT_URLS` below). The API refuses to boot without the secret key and issuer (the migration job and the ingesters do not need them), and rejects every token (logging why) whose origin is in neither list. Local values: `backend/.env.example`.

- `CLERK_SECRET_KEY`: the instance's secret key, used to fetch its signing keys. Keep it out of the frontend.
- `CLERK_ISSUER`: the instance's Frontend API URL, the `iss` claim of its tokens (for example `https://example.clerk.accounts.dev`). It is also the base64 payload of the publishable key, which is how the preview and end-to-end workflows derive it.
- `APP_CLIENT_URLS`: the frontend origins, comma-separated, also used for CORS. A token minted for any other origin is rejected with 401, and the match is an exact string comparison: list every origin the site is served from (`https://www.example.com` and `https://example.com` are two). The API refuses to boot with an entry that is not a bare origin (a path, trailing slash, space after a comma, quotes, or an empty entry from a trailing comma) and names the entry in the error; an empty list still boots. It logs `refusing token: ... authorized party "<origin>"` for a token whose origin is in neither `APP_CLIENT_URLS` nor `ADMIN_CLIENT_URLS`, so a 401 with a valid-looking token is diagnosable from the Railway logs. The preview workflow sets it to the Vercel preview URL after deploying it.

## Sign-in adoption (previews only)

A preview's database is a copy of production's, so its Users carry production's Auth Identities, which no development Clerk account has. With `APP_ENV=preview` (the preview workflow sets it), the first request from an unknown Auth Identity looks for Users whose email equals the token's `email` claim, ignoring case. If exactly one matches, that User's auth provider and subject are rewritten to the caller's, so the maintainer sees their own profile, Collections and Inventory Entries; with none or several it creates a new User as usual. Adoption runs inside the per-identity lock and transaction, so concurrent first requests adopt once. It changes only the preview's own Neon branch and nothing outside a preview: with any other `APP_ENV`, an unknown Auth Identity is a new User even when its email exists.

It trusts the `email` claim as verified, so it depends on the development Clerk instance requiring a verified email at sign-up. Keep that setting on: turning it off would let anyone adopt a User by typing an address they do not own.

## Admins (`ADMIN_EMAILS`)

`ADMIN_EMAILS`: the emails allowed to edit the catalog (ADR-0019), comma-separated, for example `owner@example.com,second@example.com`. There is no admin role or account type: a caller is an Admin when the token's `email` claim equals an entry, compared case-insensitively, and the token was minted for the Admin app's origin (below). The API refuses to boot with an entry that is not a bare email address (a name, spaces, quotes, or an empty entry from a trailing comma) and names the entry in the error. Unset, the admin routes do not exist.

- The admin routes (`/admin/...`) are registered only when `ADMIN_EMAILS` and all four `R2_*` settings are set on the API (`docs/agents/deployment/images.md`). If only one side is set, the API boots without them and logs that the allowlist is set but the R2 settings are not. Previews and CI have neither, so they have no admin surface.
- Every admin route answers 404 to a Guest, to a signed-in caller who is not listed, and to a listed caller whose token was minted for any origin outside `ADMIN_CLIENT_URLS`, with the same body, so the surface does not reveal itself. Admin traffic goes through the same edge secret and per-user rate limits as the rest of the API.
- The allowlist is only as strong as Clerk's email verification. Keep the instance requiring a verified email at sign-up (it has from the start, ADR-0015): turning that off would let anyone claim a listed address.
- The Admin app is its own web app on its own host (`admin/`, ADR-0024), linked from nowhere in the user app and absent from search engines. To a non-Admin it shows the ordinary not-found page. The user app has no `/admin` page; the address answers its ordinary not-found page.

### The Admin app's origin (`ADMIN_CLIENT_URLS`)

`ADMIN_CLIENT_URLS`: the Admin app's origins, comma-separated, validated like `APP_CLIENT_URLS` (bare origins only, the offending entry named). It is also part of CORS: the API allows the origins of both lists. A token carries the origin it was minted for, and the API decides what that origin may do:

- A token from the Admin app's origin is accepted on the admin routes and on every ordinary route, because the Admin app reads the catalog too. A listed email on such a token also sees unpublished Expansion Sets on the ordinary catalog routes.
- A token from the user app's origin keeps working on the ordinary routes, but on the admin routes it answers 404. A listed email on a user-app token is an ordinary user everywhere, and does not see unpublished Expansion Sets. So a 404 on an admin route for a signed-in Admin means the token came from the wrong origin (usually the user app, or an Admin app origin missing from `ADMIN_CLIENT_URLS`), not that the route is gone. A 401 is a different cause: the token's origin is in neither list (see the `refusing token` log above).
- The API refuses to boot when `ADMIN_EMAILS` is set and `ADMIN_CLIENT_URLS` is empty (there is no legacy mode and no insecure default), when an entry is not a bare origin, and when one origin is in both `ADMIN_CLIENT_URLS` and `APP_CLIENT_URLS`. With no allowlist the setting is not required, so previews and CI boot as before.
- Local development: anyone with `ADMIN_EMAILS` set in `backend/.env` must also set `ADMIN_CLIENT_URLS` (for example `http://localhost:3001`, the Admin app's port) or the API refuses to boot. `backend/.env.example` carries that line.

Session sharing between the apps: the Admin app has no sign-in page, so an Admin signs in through the user app and the Clerk session carries over to the Admin app. A Clerk production instance shares its session across subdomains of one domain, which is why the Admin app lives on a sibling subdomain of the user app's host. If the user app ever moves to another domain, the Admin app needs a Clerk satellite domain (out of scope for ADR-0024). Whether the development instance shares the session from `http://localhost:3000` to `http://localhost:3001` has not been checked in a browser; if it does not, the Admin app needs a sign-in route of its own.

Rollout order matters, because nothing enforces it. `preserve()` in `railway.ts` keeps an existing `CLERK_SECRET_KEY` and `CLERK_ISSUER` but never creates them, and the migration runs before the new API starts. Set `CLERK_SECRET_KEY`, `CLERK_ISSUER` and `APP_CLIENT_URLS` (the production frontend origin) in Railway production before merging, or the migration deletes every user and drops the old auth tables while the new API exits at boot and the old one keeps running against the changed schema.

The Clerk session token must carry the `email` and `name` custom claims (`scripts/clerk-setup.sh` adds them). A token without an email claim is rejected.

The first authenticated request creates the user and profile; the migration that introduced this deletes every existing user, with their Collections and Inventory Entries, once, when it first runs on a database.
