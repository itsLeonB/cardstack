# Card Category and Card Tag are first-class, filterable concepts; other Pokémon-specific facets stay in `attributes`

The replacement ingestion source (`asia.pokemon-card.com`) exposes a comprehensive filter form (9+ facets) we want to mirror. Most of those facets — energy type, weakness, resistance, HP range, retreat cost, evolution stage — are Pokémon battle mechanics with no cross-Game meaning (exactly what ADR-0001 already keeps out of fixed columns, in `cards.attributes` JSONB). Two facets don't fit that pattern: `cardType` (Pokémon/Trainer/Energy, a single-select radio in the source form) and the subtype/special-marker tag fields (`pokemonTag`/`trainersTag`/`energiesTag`/`spPokemon`, all multi-select checkboxes). Every trading card game divides its cards by some primary, mutually-exclusive structural kind, and layers secondary non-exclusive labels on top of that — the *mechanism* generalizes across Games even though the vocabulary of values doesn't. We modeled these as Card Category (first-class column, exactly one per Card) and Card Tag (a generic multi-valued label set per Card), rather than burying them in `attributes` where they'd be equally valid but harder to filter on efficiently — the same rationale ADR-0001 already used to keep `rarity`/`image_url` first-class.

## Considered Options

- Put everything (including Category and Tag) in `attributes` JSONB, staying maximally consistent with ADR-0001. Rejected: unlike HP/weakness/etc., Category and Tag are structurally present in essentially every TCG, not a Pokémon-only concept, and filtering is the explicit reason this modeling pass exists.
- Model Category and Tag as Pokémon-specific columns now, generalize later if Riftbound needs it. Rejected: the source's own UI already draws the single-select/multi-select line for us (radio vs. checkbox), so there's no ambiguity to defer — doing it right costs the same as doing it Pokémon-specific.
