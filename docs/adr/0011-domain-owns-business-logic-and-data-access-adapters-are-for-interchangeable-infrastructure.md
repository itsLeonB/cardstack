# Domain owns business logic and its data access; adapters are for interchangeable infrastructure

`internal/adapters/` is not a blanket home for anything outside `internal/domain/entity` — it's for modules with a real Adapter seam, where more than one implementation genuinely exists or is plausible: `adapters/ingestion/pokemonasia` already replaced `adapters/ingestion/tcgdex` once; `adapters/http` could swap HTTP frameworks; `adapters/repository`'s GORM/Postgres access could swap ORMs or drivers; `adapters/core/service/session_cache.go` is a cache, an infrastructure concern by nature. A Service and its Repository for actual business logic (e.g. `CatalogService`, `CatalogRepository`) don't get this treatment: interface and implementation live together, one file, under `internal/domain/`, because no second implementation is realistically coming — per the codebase-design principle "one adapter means a hypothetical seam, two adapters means a real one," splitting them across a `domain`-interface / `adapters`-implementation boundary manufactures a seam nothing actually varies across. The interface itself still exists — mockery mocks it for the service's own unit tests (see `docs/agents/testing.md`) — but that's an internal seam the module's tests use, not a caller-facing Adapter seam, so it doesn't need a separate package.

`catalog_service.go`/`catalog_repository.go` were originally split this way (domain declares the interface, `adapters/core/service`/`adapters/repository` provide the implementation), modeled on `health_service.go`'s existing shape. Corrected during review on `itsLeonB/cardstack#10`: `health_service.go` turned out not to be a validated precedent for this question at all — it has no repository dependency, so the split there never had to answer whether domain logic belongs in `adapters/`.

## Considered Options

- Keep the original domain-interface / adapters-implementation split, mirroring hexagonal-architecture convention where database access is always an adapter. Rejected: nothing in this codebase's real, near-term plans makes `CatalogRepository`'s or `CatalogService`'s implementation interchangeable — there's exactly one Postgres-backed implementation, ever — so the split was a hypothetical seam, not a real one.
- Drop the interface entirely and depend on the concrete struct directly. Rejected: mockery-based service-level testing still needs an interface to generate a mock against — a genuine internal seam, just not one that needs its own package.

## Consequences

New backend business logic (a Service and its Repository) defaults to `internal/domain/<name>/`, interface and implementation together in one file, unless a second real implementation is already in view. `internal/adapters/` stays reserved for genuinely swappable infrastructure: HTTP transport, caching, ingestion sources, background jobs, and DB driver plumbing that could plausibly change independent of the business logic sitting on top of it. `session_cache.go` and the HTTP/ingestion/job adapters were already correctly placed and are unaffected.

An earlier attempt to pull `catalog_service.go`'s `toExpansionSetSummary`/`toCardSummary` mapper functions out into a standalone `internal/domain/mapper` package failed with an import cycle: `domain/mapper` needed `domain/service`'s DTO types (`CardSummary`, `ExpansionSetSummary`, etc.), while `domain/service` needed to import `domain/mapper` back to call the mappers, so the functions stayed inlined (unexported) in `catalog_service.go` instead. That cycle is resolved now that the DTOs (`PaginationMeta`, `ExpansionSetSummary`, `SeriesSummary`, `SeriesBrowseResult`, `RaritySummary`, `CardSummary`, `CardFilter`) live in their own `internal/domain/dto` package rather than in `domain/service`: `domain/mapper` imports `domain/dto` (plus `domain/entity`/`domain/repository` for the source types) and never needs to import `domain/service`, so `internal/domain/mapper/catalog_mapper.go` now holds the exported `ToExpansionSetSummary`/`ToCardSummary` functions, and `catalog_service.go` calls them instead of inlining the conversions.
