# Scan corrections are recorded with their photo in a private bucket, and the client supplies the Detection

The matcher is provisional (ADR-0018, ticket 07 still open) and the operator needs to know which Cards it is least sure of and which photos it handles badly, so the app now records what the matcher said and what the user finally chose. This reverses the stance of the card-scanning and binder-scanning specs that photos are processed in memory and never stored by Cardstack: a photo is now kept, but only when the user changed the matcher's answer.

When a Draft Addition or a Page Review is confirmed, the client posts one `scan_feedback` row per Scan or cell, in a separate best-effort call after the placement call succeeds. The placement never waits for it, and a failed feedback call loses analytics, not the user's cards. Abandoned reviews, Removed Scans and a failed match the user leaves Unidentified record nothing. A row holds the user, the source (`card_scan` or `binder_page`), a kind (`confirmed`, `switched`, `reprint`, `empty`, `unidentified` or `placed`), the Detection, the chosen Card with its rank and whether it came from the top-5 or the Reprints list, and for a Correction an image key. A confirmation stores no image, so a correction rate per Card can still be computed. A binder row keeps the whole Page photo with the grid and corners used to cut it, so any cell crop can be rebuilt; a card-scan row keeps the photo that was matched.

The Detection is stored as the opaque JSON the client received from `/scan/match`. The server keeps no match results, and writing one row per match call would also record the reviews that are never confirmed. Trusting the client is acceptable because the data is read only by the operator, and a field the match response gains later (a model name, a new score) is captured with no schema change.

Photos go to a new private R2 bucket with its own scoped credential, never the public image bucket of ADR-0016. The client asks the API for a presigned PUT under a server-chosen key `<profile id>/<uuid>` (the caller's profile, which is how the backend keys ownership) with a signed content type and a short expiry, uploads straight to R2 (the bucket's CORS allows the frontend origin), then posts the feedback rows. On that post the API checks, for each key, that it sits under the caller's own prefix, that the first bytes carry a JPEG signature, and that the object is under a size cap; an object that fails is deleted and its row refused. A batch holds at most 100 rows and URL minting counts against the existing per-user rate limit. Card scan keeps its resolved Scans' photos and Detections in IndexedDB, keyed by user and Collection, so a refresh does not lose a Correction's photo; Page Review already does this and now also keeps the Page photo.

Photos and rows are kept until the operator deletes them by hand. There is no expiry job, no account deletion to cascade from (none exists, and there is no Clerk webhook), and no notice on the scan screens; the operator deletes a user's data with one SQL delete and a prefix delete in the bucket.

## Considered Options

- Upload through the API like `/scan/match` does, with a size cap. Rejected by the operator in favour of the presigned PUT of ADR-0019, so the API does not carry the bytes.
- Write a server-side row at every `/scan/match` call and have the client send only a match id. Rejected: it records reviews that are never confirmed and puts a write on the hot path.
- Persist nothing for a Draft Addition after a refresh and record such a Correction without its photo. Rejected so card scan and Page Review behave alike.

## Consequences

R2 cannot cap an object's size in a presign, and any signed-in user can mint a URL, so an oversized or non-JPEG object can land in the bucket before the confirm step catches it. The checks at confirm bound what a row can point at, not what a caller can upload, and an uploaded photo that is never confirmed stays in the bucket as an orphan; the operator accepts both. `ObjectStore` gains a way to read an object's size. The Detection column is only as honest as the client that sent it. Neither the bucket nor the rows are visible in the product; the operator reads them with SQL and the bucket's own tools, and an admin view is left until the questions asked of the data are known. Storing photos of a person's binder is a privacy change the operator takes on without a notice for now; it should be revisited as soon as anyone but the owner scans, and account deletion will have to remove these rows and objects when it exists.
