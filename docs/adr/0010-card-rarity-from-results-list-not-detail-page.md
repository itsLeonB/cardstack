# Card Rarity is sourced from the results-list Kelangkaan filter, not the card detail page; enumeration drops regulation partitioning

Ticket 04's ingester shipped scraping `section.expansionColumn span.alpha` on each card's detail page into the card's rarity code. Verified live (2026-09-27) that this field is actually the card's **Regulation Mark** (e.g. "I", "J" — see `CONTEXT.md`), not its print rarity ("Kelangkaan" in the site's own Indonesian UI) — the real rarity isn't present on the detail page at all. It's only derivable from the results-list page's `rarity[]=N` filter (an undocumented numeric id per code, e.g. `1=C`, `15=SAR`, ~22 values total), read the same way the ingester already reads `regulation=N`: issue the filtered query and note which card ids it returns. Confirmed live that the ~22 rarity buckets are mutually exclusive and jointly exhaustive — their union exactly equals a set's true total card count — unlike `regulation`'s partitions (see below).

Separately, `regulation=1/2/3` (Standar/Luas/Lainnya), used to both enumerate cards and opportunistically tag a best-effort `attributes.regulation` format-legality label, was found to undercount: one real set had 199 cards but only 178 were reachable via the union of `regulation=1/2/3`, while the single value `regulation=all` reliably returned the true, complete total on every set checked. `regulation=3` ("Lainnya") returns zero cards site-wide and matches no official Pokémon TCG format (confirmed via primary-source research, `.scratch/cardstack-mvp/research/pokemon-tcg-regulation-marks.md`) — Play! Pokémon and the site's own rules page recognize exactly two Regulation-Mark-defined formats, Standard and Expanded, not three. Enumeration now issues a single `regulation=all` pass per set instead of three partitioned passes, removing the need for the partition/dedup logic entirely.

## Considered Options

- Keep partitioning by `regulation` for rarity too (i.e., combine `regulation=N&rarity=M` in one request). Rejected: confirmed live that combining the two params zeroes out results — they don't compose on this site.
- Hardcode the rarity-id-to-code mapping, mirroring the existing hardcoded `regulation` labels. Rejected: unlike `regulation`'s three fixed, documented values, `rarity[]`'s numeric ids are undocumented and only knowable from each page's own filter-checkbox labels; parsing them dynamically is free (already-fetched markup) and self-updating if the site ever adds a 23rd code, consistent with `rarities`' own find-or-create philosophy (ADR-0009).
- Keep deriving `attributes.regulation` (Standar/Luas/Lainnya) from the `regulation` query partition, alongside a new Regulation Mark field. Rejected: which marks are Standard-legal is an annually-moving floor (confirmed via research: the floor has moved on every rotation since 2020, most recently Jan 2026), not a fact worth freezing at ingestion time; "Lainnya" isn't a real format; and the real Regulation Mark, once captured correctly, is a strictly better and equally free (same detail-page request) per-card signal than the derived label ever was.

## Consequences

The regulation-partitioned enumeration and its overlap-dedup logic are removed entirely, replaced by one paginated pass per set. A new rarity-partitioned sweep (one paginated pass per discovered rarity code, most returning zero quickly) is added as the authoritative source of Card Rarity. `attributes.regulation` (the computed Standar/Luas/Lainnya label) is replaced by the raw per-card Regulation Mark letter; a future consumer wanting Standard/Expanded legality computes it from the raw mark against the *current* rotation floor, not from data frozen at ingestion time. Existing `rarities` rows populated with Regulation Mark letters (from the bug) are stale once a corrected re-ingestion resolves cards to the real Kelangkaan-coded rows, and need a one-time cleanup pass.
